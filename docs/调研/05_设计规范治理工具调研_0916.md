# 设计规范治理工具调研（2026-09-16）

> **调研动机**：用户提出「有没有类似 OpenSpec 的方法来规范开发规范？OpenSpec 是针对开发流程的技术，那针对开发规范的呢？」
> **调研方法**：Firecrawl 实查（非推测），原始材料存 `.firecrawl/`（已 gitignore）
> **结论摘要**：这类技术**存在**，最匹配的是 `@lapidist/design-lint`；**建议借鉴其规则清单而非直接引入工具**。

---

## 一、核心问题：为什么"写规范"不管用

本次调研最重要的收获，是找到了**行业级的问题诊断**，两句话直击本质：

> **"Agents ignore specs. Writing the spec is the easy half; most tools have nothing that _makes_ the implementation honor it."**
> —— `cameronsjo/spec-compare`（对比 19 个 spec-driven 工具的研究项目）

> **"Even with a well documented design system, drift begins immediately."**
> —— `@lapidist/design-lint` 作者 Brett Dorrans

> **"Traditional linting tools don't catch these issues – ESLint and Stylelint care about syntax, not whether your team is following tokens or components correctly."**
> —— 同上

**对本项目的意义**：这三句话证实了本项目踩过的坑是**行业通病**，且指出了唯一出路——
1. 写规范是"简单的一半"（本项目的 304 行规范文档即属此半）
2. 缺的是**让实现遵守的机制**（本项目的 `check-ui-rules.mjs` + `AGENTS.md` 内嵌摘要卡即属此半）

## 二、最匹配的工具：`@lapidist/design-lint`

| 项 | 内容 |
|---|---|
| 定位 | **Design System Runtime (DSR)**，不是通用 linter |
| 开源时间 | 2025-08 |
| 仓库 | https://github.com/bylapidist/design-lint |
| 文档 | https://design-lint.lapidist.net |
| 基础格式 | DTIF（作者自研的 Design Token Interchange Format） |

### 能力清单

| 能力 | 说明 | 对本案的价值 |
|---|---|---|
| **Token awareness** | flag 所有 raw value（`17px`、`#7c3aed`），对照配置的 token 约束 | 已在自研脚本实现 |
| **Component usage 强制** | 若系统提供 `<Button>`，则裸 `<button>` + 临时样式会被报错 | **★ 本案完全缺失，最该借鉴** |
| **Auto-fix** | `--fix` 自动替换废弃 token（如 `oldBrandColor` → `newBrandColor`） | 大更新迁移 token 时极有用 |
| **Policy 层** | 集中管理的 guardrails，供多团队消费 | 团队协作场景 |
| **多语言支持** | JS/TS/CSS/SCSS/Less，含内联样式（JSX object literal） | 覆盖本案技术栈 |
| **CI 集成** | GitHub Actions 示例 + SARIF 输出 + JSON | 与本案 CI 计划一致 |
| **可扩展** | 自定义 rules / formatters / token path transforms | 可与自研脚本共存 |

### 文档信息架构（可借鉴）

```
docs/
├── configuration.md         # 规则级别、插件激活
├── configuration-presets.md # recommended / strict 等预设
├── rules/index.md           # 按类别分组的规则参考
├── migration.md             # 版本迁移
├── plugins.md               # 自定义规则插件
├── policy.md                # 集中治理的 guardrails
└── ci.md                    # CI 集成（GitHub Actions）
```

**采纳建议**：本项目规范文档的结构可参照此分层——**配置 / 规则 / 策略 / CI** 四段式。

## 三、Design Tokens 权威标准：W3C DTCG

| 项 | 内容 |
|---|---|
| 全称 | Design Tokens Community Group（W3C 社区组） |
| 状态 | 行业事实标准 |
| 核心 | token 用 `$value` / `$type` / `$description` 描述（`$` 前缀为规范标志） |
| 生态 | Tokens Studio、Style Dictionary 等均支持 |

**对本项目的意义**：当前 `index.css @theme` 是**浏览器可用的形式**，未采用 DTCG 的 JSON 描述。
**结论**：本案规模（17 个颜色令牌 + 少量尺寸）**不必引入 DTCG 格式**，保持 CSS 变量即可；但命名与语义分层可参考其做法。

## 四、Token Lint 规则清单（可直接照搬）

来源：Always Twisted《Linting Your Design Tokens》+ DTCG 规范

### 关键规则（Critical）

| 规则 | 含义 | 本案适用性 |
|---|---|---|
| **No Broken References** | token 引用必须指向存在的 token | ⚠️ 本案用 CSS 变量，浏览器已兜底，但可校验 `var(--x)` 是否存在 |
| **No Circular References** | 禁止循环引用 | ✅ 可加 |
| **Type-Value Matching** | 类型与值匹配（color 不能是 `"16px"`） | ⚠️ CSS 变量无类型，价值有限 |
| **Complete Token Structure** | 每个 token 结构完整 | ⚠️ 同上 |

### 质量规则（Quality）

| 规则 | 含义 | 本案适用性 |
|---|---|---|
| **Naming Convention** | 命名规范一致 | ✅ 可校验（如必须 `--color-*` 前缀） |
| **No Duplicate Values** | 禁止重复值（两个 token 同色） | ✅ **可加**——本案 `--color-surface` 与 `--color-inverse` 值相同，属**有意为之**（语义不同），需规则支持白名单 |
| **Required Tokens Present** | 必需 token 必须存在 | ✅ 可加（如必须存在 `--color-signal`） |
| **Colour Contrast Compliance** | 颜色对比度合规（WCAG） | 🎯 **高价值，本案未做**——可校验 `--color-ink` on `--color-surface` 的对比度 |
| **Dark Mode Completeness** | 暗色模式 tokens 完整 | ⏳ 本案暂无暗色模式，未来若加需此规则 |
| **Reference Depth Limits** | 引用层级不超限 | ⚠️ 本案层级浅，价值低 |

### 可选规则（Nice-to-have）

- Token Documentation（每个 token 有描述）
- Semantic Naming（语义化命名）
- No Unused Tokens（无未使用 token）

### 关键结论（原文摘录）

> **"Critical Gap: Most SDD tools excel when requirements are clear upfront but struggle with iterative changes."**
> （多数 SDD 工具擅长"需求明确的前期"，却在"迭代变更"上乏力）

> **"OpenSpec — Purpose-built for modifications with delta format (ADDED, MODIFIED, REMOVED)."**
> （OpenSpec 专为修改而生，用 delta 格式）

**对本项目的意义**：本项目**已经在用 OpenSpec**，且它被公认为**最适合存量项目的迭代变更**——这条路线选对了。

- **Scalability Concerns**：何时 SDD 收益大于开销？

## 六、结论与采纳建议

### 是否直接引入 `@lapidist/design-lint`？

**不建议**。理由：

| 理由 | 说明 |
|---|---|
| 生态早期 | 2025-08 开源，v8 为新架构（有 migration 文档，说明刚做大改） |
| 格式自研 | 基于作者自研的 DTIF，非 DTCG 标准，存在锁定风险 |
| 与现有链路重复 | 本案已有 `check-ui-rules.mjs` + pre-commit + CI |
| 规模不匹配 | 本案 17 个颜色令牌、13 个组件，引入重型运行时收益有限 |

### 建议采纳的 4 项

| # | 采纳项 | 落地方式 |
|---|---|---|
| **1** | **Component usage 强制检查** | 自研脚本新增规则：检测"有组件却用裸元素"（如已有 `Modal` 却写裸弹窗） |
| **2** | **10 条 token lint 规则** | 择优加进自研脚本（重点：Colour Contrast、Required Tokens、No Unused） |
| **3** | **规范文档四段式结构** | 配置 / 规则 / 策略 / CI |
| **4** | **`--fix` 自动迁移思路** | 大更新迁移 token 时，脚本提供自动替换（而非纯报错） |

### 已证实正确的既有路线

| 本项目做法 | 行业验证 |
|---|---|
| `AGENTS.md` 内嵌规范摘要 | ✅ 解决"Agent 不读文档" |
| `check-ui-rules.mjs` 机械校验 | ✅ 解决"Agent 无视规范" |
| CI 集成 | ✅ 与 design-lint 的 CI 方案一致 |
| 用 OpenSpec 管变更 | ✅ 被公认为最适合存量项目的 delta 方案 |
