# 动效方案 × 改进意见 · 并行开发边界约定

> 版本：v1.0 ｜ 日期：2026-09-13 ｜ 状态：**待确认**
> 目的：判定 `动效与交互升级方案.md`（下称 **方案 A**）与 `多Agent工作台-改进意见.md`（下称 **方案 B**）能否并行开发，并划定具体边界。
> 方法：只读遍历项目源码，逐条核验两份方案会触碰的文件与行段。未改动任何代码。

---

## 一、结论

**可以并行。** 交叉面很小 —— 真正双方都写的只有 **3 个文件**，其余全部单方独占。

但**不能完全放任并行**：这 3 个文件里有 2 个存在「同一函数 / 同一节点」级别的对撞，必须规定先后顺序。

| 判定 | 数量 | 文件 |
|---|---|---|
| ✅ 可立即无冲突并行 | 13 | 详见 §2 |
| ⚠️ 必须串行 | 3 | `ObservabilityView.tsx`、`useWorkbench.tsx`、`BoardView.tsx` |
| ❌ 高危 | 0 | —— 通过 §4 的三项约定可全部降至行级自动合并 |

**根本原因**：两者的性质不同。方案 A 是**视觉层纯追加**（改 CSS 类与展示层），方案 B 是**全栈功能改造**（改数据模型、并发控制、故障边界），绝大部分时候在改不同的东西。

## 三、必须串行的 3 个文件

### 3.1 `ObservabilityView.tsx` —— 风险最高

**对撞点（已实读确认）**

| 位置 | 方案 A | 方案 B |
|---|---|---|
| `ObservabilityView.tsx:79-95` | P1-4 要给 `totals.successRate` 加**数字补间**（`:234` 消费该值） | 2.11 要**改这个数的计算口径**（拆成调用成功率/一次通过率/打回率） |
| `ObservabilityView.tsx:293` | P0-2 要给 `executions.map` 的 `<tr>` 加 **stagger 类名** | 3.1 要改同一 `<tr>` 内 `:307` 的**阶段单元格内容**（英文 id → 中文标签） |

**为什么算冲突**：A 的补间**目标值**依赖 B 的口径定义 —— 如果 B 先改口径，A 的补间逻辑要重写；如果 A 先做，补间对象会在 B 合并后失效。且同一个 `<tr>` 的 `className` 与子节点内容都会被改。

**串行顺序**：**B 先落 2.11 + 3.1 → A 基于合并后的 main 重开分支再做 P1-4 / P0-2。**

> 补充核查：2.11 的口径拆分**需要同时改后端** `backend\src\routes\agents.ts:33-60`（权威值 `executionStats()` 在这里算，`runs===0 ? 100 : ...`）与前端 `:79-95`。这进一步说明它必须先落定。

### 3.2 `useWorkbench.tsx` —— 条件性冲突

**对撞点**

| 方案 | 要改什么 |
|---|---|
| 方案 B | 3.5 拆 Context（**整文件结构性重排**，`:452-505` 单 Provider 承载 40+ 字段）；2.10 `sendChat` 复用长连接（`:350-373` 每次 `new WebSocket`，已确认）；3.4 `refresh()` 加 error state（`:163-175`） |
| 方案 A | 若要在此加「视图切换过渡」的 state，则与 3.5 直接对撞 |

**解决方式（推荐）**：**方案 A 全程不碰这个文件**。视图过渡改为只用 `App.tsx` 容器的 CSS keyframe 实现（这正是 `动效与交互升级方案.md` §P0-1 的原始设计 —— 只包裹内容区）。这样 A 零风险，B 独占比文件。

**若 A 确实需要新 state**：则 B 3.5 先落，A 后做。

### 3.3 `BoardView.tsx` —— 中等风险

**对撞点**：两者都改 `TaskCard` 组件。

| 位置 | 方案 A | 方案 B |
|---|---|---|
| `BoardView.tsx:71` | P2-2 卡片 hover（`.qs-card.qs-interactive`）、P0-2 `:334` 的 `list.map` stagger | —— |
| `BoardView.tsx:53, 143-155` | —— | 1.1 按钮 pending/disabled（**注：前端这部分已部分落地**，已有 `confirming` state + catch→toast） |
| `BoardView.tsx:263-269` | P1-1 卡片状态流转动效 | 1.3 加「重试当前阶段」按钮 + `void` → catch→toast |

**为什么只是中等**：改的是**不同行段**，merge 大概率自动成功。但 `1.3` 的「失败态卡片」语义与 A 的「卡片状态流转动效」**指向同一个视觉对象**，需要人工确认视觉优先级 —— 失败态应该用什么颜色/动效，得两边商量。

**建议**：B 先落（含「重试当前阶段」按钮），A 再追加 hover 与 stagger 类名。

## 四、三项约定：把残余冲突降到行级自动合并

这是让并行真正安全的操作性约定，**建议写进两边的开发规范**：

### 4.1 只增类，不改存量类

> 方案 A 只**新增** `.qs-motion-*` 类，**绝不修改**存量 `.qs-*` 类的既有属性。

**理由**：`index.css` 是 A 的核心战场，也是唯一的全局共享资源。若 A 去改 `.qs-card` / `.qs-btn` 的既有值，会波及所有引用方；若只追加新类，改动面就被锁死在「纯追加」，merge 永不冲突。

**特别注意**：`动效与交互升级方案.md` §3.3 提出**替换**现有 `--dur-fast`（160→150ms）与 `--ease-standard`（换成 Carbon 曲线）。这是**修改存量令牌**，建议改为**新增** Carbon 令牌（`--dur-micro` / `--ease-entrance` 等）并保留旧值，等 B 合并完成后再统一清理。这样避免任何潜在的跨文件影响。

### 4.2 不动 JSX 结构

> 方案 A 的动效全部走 **CSS 类 + inline `style={{ '--i': idx }}`**，不改 JSX 树结构、不打乱现有 className 的 token 顺序。

**理由**：把 `BoardView` / `ObservabilityView` 的冲突从「行级重写」降为「属性级追加」。

**具体到最高危的 `ObservabilityView`**：
- A 的 stagger **只在 `<tr>` 上追加 `className`**，不碰 `<td>` 内任何内容节点 → 与 B 3.1 改 `:307` 单元格内容形成行级隔离
- A **承诺不改** `:79-95` 的 `totals` 计算，只消费其输出值

### 4.3 不动 store 结构

> 方案 A 不修改 `useWorkbench.tsx` 的任何 state / Context 结构，视图过渡只用 `App.tsx` 容器 + CSS keyframe。

**理由**：`useWorkbench.tsx` 是 B 3.5 的结构性重排目标，也是唯一一个「整文件级」冲突源。A 一旦不碰它，冲突归零。

### 4.4 共享类型文件的分工

> `packages\shared\src\types.ts` **由方案 B 独占**。
> 方案 A 若需新类型（如未来做「思考流」的事件类型），走**独立新文件** `packages\shared\src\ws-protocol.ts` 追加。

## 五、Branch 策略

```
main
 ├── feat/codex-improvements   (方案 B，全栈改造)
 └── feat/motion               (方案 A，视觉层纯追加)
```

**规则**

1. **两个长期分支**，从同一 `main` 切出。
2. **单写者文件锁定**：`ObservabilityView.tsx`、`useWorkbench.tsx`、`BoardView.tsx` 设为单写者 —— 同一时间只允许一个分支改，另一方以 follow-up commit 追平。
3. **短周期合并**：每个 PR ≤ 1 天，采用 `rebase onto latest main → 快进合并`，避免 rebase 地狱。
4. **关键顺序**：**方案 B 先合并 `ObservabilityView.tsx` 与 `useWorkbench.tsx`，方案 A 再基于合并后的 main 重开分支**，而不是双方各自改完再互 rebase。
5. `packages\shared\src\types.ts` 由 B 独占。

## 六、依赖关系澄清（三处重要修正）

### 6.1 B 的 1.3 `failed` 列 —— 不是 A 的硬前置

**核验发现**：`backend\src\db\ensure.ts` 的 tasks 表**没有** `failed` / `last_error` 列。B 的 1.3 当前设计是「失败时把原因写进 `stage_note` 文案」（`service.ts:378-385`），**并非新增列**。

- A 若只是给**现有** `awaiting` / `progress` 状态做动效（`BoardView.tsx:74`）→ **无需等 B**
- A 若要为**新增的「失败」态**做专属视觉（红色卡片 + 抖动 + 重试按钮动效）→ **需要 B 先定义该状态的语义**

**建议**：把失败态动效归入「B 1.3 落地后的 follow-up」，不塞进 A 的首批范围。

### 6.2 B 的 1.6 图片落盘 —— 不是前置，但强耦合

**核验发现**：当前图片是 **dataURL 直存**（`types.ts:138`），`Thumb` / `ImgThumb` 用 `<img src={dataURL}>` + `onLoad` Spinner（`ContentDeliveryView.tsx:88-133`）。

**关键含义**：dataURL 是**本地即时解码**，图片加载态动效**几乎不可见**。B 1.6 改为落盘 URL 后，图片变成真网络加载，A 的加载态动效才有意义。

**建议**：**B 1.6 先于 A 的交付物图片加载动效**。二者不阻塞编译，但顺序反了等于白做。

### 6.3 「思考流替代 Spinner」—— 是独立第三条工作线

**核验发现（重要）**：方案 B 的 20+ 条中 **没有任何一条**涉及后端暴露 Agent 中间过程。

具体证据：
- 全仓 `backend/src` 搜索 `thinking` / `思考中` / `stream` → **零命中**
- `agents\llm.ts:120` 后端 LLM 调用为 **`stream: false`**

也就是说，要做「思考流」需要**新增**三样东西：
1. 后端 LLM 改为流式（或至少阶段性上报「正在调用 X 工具 / 检索了 Y 文档」）
2. `packages\shared\src\ws-protocol.ts` 新增事件类型（**不要写在 `types.ts`**，避免与 B 抢文件）
3. 前端消费与渲染

**结论**：这是**独立第三条工作线**，既不依赖 A 也不依赖 B，但工作量不小。**建议单独评估是否纳入本次范围。**
