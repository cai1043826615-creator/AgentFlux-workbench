# 「每日热点」多信息源接入调研报告

- **调研对象**：中国「电商多 Agent 工作台」每日热点面板（`backend/src/knowledge/hot.ts` + `backend/src/knowledge/attention.ts`）
- **当前实现**：单一匿名源 `https://aihot.virxact.com`，15 分钟缓存，关键词子串匹配分层
- **调研方式**：全部候选端点使用 `node -e "fetch(...)"` 真实 HTTP 探测（超时 10 秒），关键端点做 3 次重试稳定性测试
- **调研时间**：2026-09-11
- **本机出口 IP**：113.108.106.159（多站点 403 响应头中回显，见下文证据）
- **本报告不改动任何代码**

## 一、结论摘要

### 1.1 问题复现（为什么必须换/加源）

实测 `https://aihot.virxact.com/api/v1/hot-topics`（HTTP 200，961ms，6097 字节），榜首即：

```
{"rank":1,"id":"cmtugou9e1cddrofptz3jwh4j","title":"Apple 发布首款折叠屏 iPhone Duo，起售价 $1,999",
 "source":{"name":"Apple：Newsroom（RSS）"}, ...}
```

该源是 **AI 行业资讯聚合**，与电商运营关注域无交集。而现有匹配逻辑（`attention.ts` 第 127–133 行）是**无权重、无作用域、无负向词的子串包含**：

- `竞品动态` 关键词含 `发布`、`上新`、`定价` → 「Apple 发布折叠屏 iPhone」必然命中；
- `平台规则` 关键词含 `天猫`/`淘宝`/`京东`/`拼多多` → 任何顺带提及平台的科技新闻都会命中；
- 分层用 `sourceCount >= minimumSources(2)` 判「必看」（`attention.ts` 第 158 行）→ AI 圈多个信源跟进同一条科技新闻，反而更容易被判 strong 进「今日必看」。

**根因不是源太少，而是「源领域」与「关注域」之间缺少约束关系。** 因此本方案的核心不只是加源，还要给每个源标注作用域。

### 1.2 推荐源（接入优先级）

### 1.3 最关键的三条风险

1. **合规风险（高）**：微博、知乎、抖音的公共热榜**没有**可合法服务端调用的免费接口。微博 `weibo.com/ajax/side/hotSearch` 实测 403、`s.weibo.com/top/summary` 返回 Sina Visitor System 反爬页；知乎 API 实测 401，且 `zhihu.com/robots.txt` 结尾为 `User-Agent: * Allow: /tardis/jm Disallow: /`——**对非白名单 UA 全站禁止抓取**；抖音 `robots.txt` 只列出 Googlebot/Baiduspider/ByteSpider 等白名单 UA，无通用兜底授权。抖音官方榜单 API 则在文档中明写「**权限范围：针对审核通过的用户开通权限**」。**若坚持要这三家，唯一合规路径是走官方开放平台审核，否则应放弃或改用 60s 自部署聚合并显式接受灰色风险。**
2. **稳定性风险（中-高）**：抖音官方 web 热榜接口 `https://www.douyin.com/aweme/v1/web/hot/search/list/` 首次探测返回 200 / 64625 字节，但**随后 3/3 次均为 HTTP 200 且 body 长度为 0**——这是最危险的一类失败（状态码正常、内容为空，现有 `fetchJson` 只在 `!res.ok` 时抛错，会直接 `res.json()` 抛异常）。同类证据：DailyHotApi 公共演示域 `api-hot.imsyy.top` **DNS 已失效**、`tenapi.cn` 502、`api.vvhan.com` DNS 失效、`api.oioweb.cn` 自签证书错误、RSSHub 公共实例 `rsshub.app` 10 秒超时。**结论：公共第三方聚合 API 不可作为生产依赖，必须自部署或直采源头。**
3. **不可达风险（中）**：多家中国电商媒体对机房/境外 IP 有 WAF 拦截。**亿邦动力 `www.ebrun.com` 全部路径（`/`、`/news/`、`/rss.xml`、`/home/`）实测 403 Forbidden**，响应头回显本机 IP；**36氪 `36kr.com/feed` 返回火山引擎安全检测页**；海关总署 412；QuestMobile 403；国家统计局数据 API `data.stats.gov.cn` 403（`reason:UrlACL`）。这些源在本机（及任何云服务器）都不可用，不要写进方案。

## 五、建议的接入架构

### 5.1 总体分层：按「源权威度」而非「关键词命中」决定层级

现有逻辑的缺陷是**层级完全由关键词命中 + sourceCount 决定**，与源本身是否权威无关。建议改为三层：

```
第 1 层｜权威事实层（直接进「必看/浏览」，无需关键词命中）
  ├─ 电商派 7×24h 快讯   https://www.pai.com.cn/news/
  ├─ 网经社 24h 播报      https://www.100ec.cn/list.html
  └─ 国家统计局 数据解读   https://www.stats.gov.cn/sj/sjjd/
  → 特点：垂直/官方、低噪音、服务端可直取。这些源出现的条目天然属于「电商关注域」。

第 2 层｜行业媒体层（需命中关注域才进「浏览」）
  ├─ 卖家之家            https://www.mjzj.com/
  ├─ 抖音电商学习中心      https://school.jinritemai.com/doudian/web/home（规则入口）
  └─ 易观分析            https://www.analysys.cn/（低频，可周更）

第 3 层｜公共热点兜底层（默认只进「其他」，需强过滤才可上浮）
  ├─ 今日头条热榜          https://www.toutiao.com/hot-event/hot-board/?origin=toutiao_pc
  ├─ 百度热搜            https://top.baidu.com/api/board?platform=wise&tab=realtime
  └─ 60s 自部署（微博/抖音/知乎/头条）  自建 /v2/weibo|douyin|zhihu|toutiao
  → 特点：噪音极大。必须叠加「负向词表 + 多词命中 + 源作用域」三重过滤，否则重演
     「Apple 发布折叠屏 iPhone → 竞品动态 → 今日必看」。
```

### 5.3 聚合、去重与缓存

**去重（三层）：**
1. URL 规范化精确去重：去 `#fragment`、去 `utm_*`/`from`/`spm` 等跟踪参数，小写 host，去末尾 `/`。
2. 标题归一后精确去重：去空白、全角转半角、去中英文标点、去「独家｜」「重磅」等前缀。
3. 近似去重：归一标题做 3-gram Jaccard 或 SimHash，阈值 0.8 视为同一事件，合并为一条并把各源写入 `sources[]`。

**事件合并后的数据结构**（替代现有 `RawHotItem.sourceCount`）：

```ts
interface RawHotItem {
  id: string;
  title: string;
  summary: string | null;
  url: string | null;
  latestAt: string | null;
  sources: { id: string; name: string; tier: 1 | 2 | 3; url: string | null }[];  // 新增
  sourceCount: number;       // = sources.length，保留以便兼容
  maxSourceTier: 1 | 2 | 3;  // 新增：最有权威的那个源的层级
  domains: { id: string; label: string }[];
}
```

**缓存分层**：现有 `knowledge_hot_cache` 是单 key（`daily-hot`）+ 15 分钟 TTL 的单源缓存。建议改为**按源打 key**（`hot:<sourceId>`），这样：
- 单源失败只降级该源，不影响其他源（现状是一个源挂掉整块面板 stale）；
- 高频源（热榜）TTL 15 分钟，低频源（统计局、网经社）TTL 6–12 小时，减少无谓请求；
- 面板组装时做「部分可用」状态，而不是非 live 即 stale/unavailable。

**空响应防御（必须加）**：实测抖音端点会返回 `HTTP 200 + body 长度 0`。现有 `fetchJson`（`hot.ts` 第 41–47 行）只在 `!res.ok` 时抛错，随后 `res.json()` 会抛 `SyntaxError: Unexpected end of JSON input`。建议在解析前校验 body 非空且为合法 JSON，否则按源失败处理。

**合规治理**：`sources[]` 中带 `complianceRisk`，中/高风险源默认 `enabled: false`，需用户在设置里显式开启并显示风险提示；面板中每条热点保留原始链接（只展示标题+链接+摘要片段，**不落库全文**），降低版权风险。

### 5.4 落地顺序建议

1. **第一步（最小改动，收益最大）**：接入 **电商派快讯** + **国家统计局数据解读**，并把 `attention.ts` 的匹配改为「强/弱关键词 + minHits + 源作用域」。这一步就能消除绝大部分假阳性，且两者风险低、稳定。
2. **第二步**：接入 **网经社 24h 播报**（补平台规则与监管维度）。
3. **第三步**：部署 **60s 自部署实例** 或直采 **今日头条热榜 JSON**，作为「其他」层的公共热点兜底（必须带 `excludeKeywords` 负向词表）。
4. **第四步**：保留 `aihot.virxact.com` 但**降级**为 tier 3 且 `applyToSourceIds` 不包含任何电商关注域——或直接关闭。

## 六、待确认事项

1. **跨境电商是否需要？** 卖家之家（`mjzj.com`，200 可读）与雨果跨境是跨境向；若工作台只做国内平台，可完全忽略。若需要，卖家之家可作 tier 2（无 RSS，需 HTML 列表解析）。
2. **「品类趋势」是否需要进「今日必看」？** 任务描述提到「影响选品参考，但不自动改任务」，若趋势类只做参考展示，建议给它独立的「趋势参考」分区，而不是与「必看」混排。
3. **大促日历（双11/618/年货节等固定节点）是否应作为本地静态数据？** 这类节点是确定性的（日期可预算），从外部源抓既不稳定也无必要。建议内置一份 `promo-calendar.json`，热榜源只做「节奏/话术」补充。
4. **60s 是自部署还是直连公共实例？** 公共实例已实测 `/v2/60s` 429 限流，README 也明确「每日额度有限，建议自行部署」。若走自部署：服务器出网 IP 是否会被微博/抖音风控？需要预留代理与降级。
5. **第三方聚合 API（60s / DailyHotApi 类）是否可接受作为生产依赖？** 其数据转发自微博/抖音/知乎，条款风险由使用方承担。若合规要求严格，则应放弃这三家热榜，只保留头条/百度（自用 XHR，风险中等）。
6. **内容版权策略**：面板是仅展示「标题 + 原文链接」，还是需要落库摘要/全文？前者风险低，后者需逐一评估各源转载授权。
7. **本机/服务器出口 IP 是否可能被进一步封禁？** 实测本机 IP `113.108.106.159` 已被亿邦动力（403）、QuestMobile（403）、海关总署（412）、`data.stats.gov.cn`（403 UrlACL）拦截。建议在目标部署环境重跑本报告的探测清单，确认可达性——**本报告的可达性结论仅对本机出口有效**。
8. **电商派 HTML 列表的解析选择器是否长期稳定？** 实测链接形如 `/news/<26位ID>`，class 结构未逐层记录。建议接入时固化选择器并加「条目数骤降告警」（例如从 20 条掉到 0 条即报警），而不是静默返回空面板。
