## 一、诊断结论：AI 味到底在哪

### 1.1 先说一个反直觉的结论

**你的视觉层基本没有 AI 味。** 逐项验证过的「AI 默认样式」嫌疑全部不成立：

| 常见 AI 味特征 | 本项目实际情况 |
|---|---|
| 紫蓝渐变 `from-purple-500 to-blue-500` | ❌ 全库 `bg-gradient` **0 命中** |
| 满屏 `rounded-xl/2xl` | ❌ 68 次 `rounded-[4px]` + 大结构直角 0px |
| 🎉🚀 表情符号装饰 | ❌ 仅 `✓ ⚠ ✕ ★` 共 21 个排版符号 |
| 居中标题 + 三栏 feature 网格 | ❌ 无此结构 |
| 系统默认字体 | ❌ Noto Serif SC（display）/ Noto Sans SC / JetBrains Mono 三档 |
| 零阴影堆叠 / 玻璃拟态 | ❌ 默认无阴影，规划表明确禁用 |

`index.css:3` 明确标注对齐 SPEC §4，项目已有一套自洽的 **Quiet Signal** 语言：近白画布、黑灰信息层级、衬线 Display 标题、有限紫色信号色、大结构直角、小控件 4px 圆角。

**所以「降低 AI 味」不应该是加特效** —— 那反而会破坏已有的高级感，也直接违反 `组件视效规划表.md` §0 的风格红线（禁玻璃拟态/渐变光晕/粒子堆砌）。

### 1.2 AI 味真正集中在哪里：动效与交互层

实测 + 源码双重确认，共 **9 个可定位的缺口**：

| # | 缺口 | 证据（文件:行号） |
|---|---|---|
| 1 | **hover 交互 90% 只是换颜色** | 全项目约 30 处 `transition-colors`，带空间变换的仅 3 处：`App.tsx:492`、`App.tsx:509`、`ContentDeliveryView.tsx:124`、`index.css:443` |
| 2 | **零编排 / 零 stagger** | 看板卡片 `BoardView.tsx:298`、热点卡 `HotView.tsx:786`、目录树 `KnowledgeView.tsx:42`、日志行 `ObservabilityView.tsx:270` 全部直接 `map` 渲染，无入场、无递增延迟 |
| 3 | **视图切换是硬切** | `App.tsx:459-466` 靠 `view === 'x'` 直接替换 DOM，无过渡无淡入，切页「闪一下」 |
| 4 | **所有弹窗无进出场动画** | `ui.tsx:49` 的 `if (!open) return null` 硬出现；`LeftPanel.tsx:107`、`AgentSettingsModal` 同样。反讽的是 Toast 有 `qs-toast-in`，标准不统一 |
| 5 | **缓动曲线只有 1 条且被错用** | `index.css:31` 的 `--ease-standard: cubic-bezier(0.22,1,0.36,1)` 是 ease-out 型，却套在 3 个**无限循环**动画上（`:252` busy-pulse、`:278` qs-pulse、`:520` step-pulse），导致脉冲「快冲慢回」不自然 |
| 6 | **间距 token 形同虚设** | `index.css:33-39` 定义了 `--space-1…6`，注释自承「现有内联值保持不动」，结果**全站 0 引用**；实际靠 `gap-2`(87 次)/`gap-1.5`(38)/`p-3`(14) 的手感堆叠 |
| 7 | **进度反馈两套标准** | `TaskDetailView.tsx:277-279` 进度线有 300ms width 过渡，但看板 flowbar `BoardView.tsx:106-129` 是纯静态色块 —— 同一「阶段推进」语义两种表现 |
| 8 | **动效全在服务「数据没来」** | `qs-pulse`、`qs-btn-spinner`、`animate-spin`、`qs-step-current` 共 6 处全是 loading/占位；**没有一处**服务于「操作已生效 / 状态已变化」 |
| 9 | **工程隐患** | `index.html:7-12` 三套中文字体全走 Google Fonts CDN，国内网络下 FOUT / 回退宋体，直接摧毁 `--font-display` 建立的高级感；无 `preload`、无本地兜底；**完全无暗色模式** |

### 1.3 一句话定位

> 基础设施是干净的（Tailwind v4 `@theme` 令牌齐备、`.qs-*` 语义类收敛、零第三方 UI 库纠缠、26 个源文件），**加动效不需要先重构**。
> 缺的不是「更炫的效果」，是**响应感**和**编排感** —— 每一次操作都有可感知的即时反馈，每一批元素都有节奏地出现。

## 二、优化总纲：在这个项目里，「酷炫」的正确解法

把「抓人眼球」翻译成 Quiet Signal 语言可接受的三条：

| 传统意义的「酷炫」 | 本项目的正确等价物 | 为什么更高级 |
|---|---|---|
| 大渐变光晕、粒子背景 | **空间连续性**：元素从它该来的地方来（origin-aware），到它该去的地方去 | 让界面像物理实体，而不是贴图 |
| 元素飞入、旋转登场 | **编排节奏**：一批元素按 30–60ms 递增错峰出现 | 制造「系统在有条理地工作」的暗示 |
| 弹跳、缩放、抖动 | **即时响应**：按下 70ms 内必有视觉确认（scale 0.97 / 状态变色） | 消除「我点了没」的焦虑 |

**核心公式：响应感（操作 → 反馈 < 120ms） + 编排感（批量元素错峰入场） + 连续性（空间来源可追溯）**

这三条恰好也是 `组件视效规划表.md` 已采纳的 GodUI Motion Principles「Restraint」原则（subtle beats flashy）的落地方式，方向不冲突。

## 三、动效令牌体系（先立规矩，再动手）

### 3.1 现状问题

项目现在只有 `--dur-fast/standard/deliberate`（160/220/300ms）三档时长和 **1 条** 缓动曲线，且没有区分入场/出场/用户反馈。这是所有动效「平」的根因。

### 3.2 推荐基线：IBM Carbon Motion（企业级双轨制）

选它的理由：Carbon 是 IBM 为企业级工具产品做的设计系统，明确区分 **productive（生产型）** 与 **expressive（表达型）** 两种动效，正是工作台场景的标准答案 —— 日常操作保持克制，关键时刻才允许「有情绪」。

**三种缓动 × 两种风格 = 6 条曲线**（来自 [Carbon Motion 官方规范](https://carbondesignsystem.com/elements/motion/overview/)）：

| 缓动类型 | 使用场景 | Productive（生产型） | Expressive（表达型） |
|---|---|---|---|
| **Standard** | 元素从头到尾可见（展开、排序、位移） | `cubic-bezier(0.2, 0, 0.38, 0.9)` | `cubic-bezier(0.4, 0.14, 0.3, 1)` |
| **Entrance** | 元素进入视图（弹窗、Toast、下拉展开、开关） | `cubic-bezier(0, 0, 0.38, 0.9)` | `cubic-bezier(0, 0, 0.3, 1)` |
| **Exit** | 元素离开视图（关闭弹窗、Toast 消失） | `cubic-bezier(0.2, 0, 1, 0.9)` | `cubic-bezier(0.4, 0.14, 1, 1)` |

> 例外：侧栏这类「离开视野但随时可召回」的元素，用 **Standard** 而非 Exit —— 减速离场暗示它停在视野外待命。

**时长令牌**（Carbon 六档静态值）：

| 令牌 | 用途 | 值 |
|---|---|---|
| `duration-fast-01` | 按钮、开关等微交互 | 70ms |
| `duration-fast-02` | 淡入 | 110ms |
| `duration-moderate-01` | 微交互、小展开、短距离位移 | 150ms |
| `duration-moderate-02` | 展开、系统通信、Toast | 240ms |
| `duration-slow-01` | 大展开、重要系统通知 | 400ms |
| `duration-slow-02` | 背景变暗 | 700ms |

**Carbon 的三条硬性禁令**（与项目现状直接冲突，必须改）：
1. **禁止**使用带弹跳 / 拉伸 / 急停的缓动曲线
2. 微交互必须落在 **90–120ms** 区间
3. **重复出现几十次甚至上百次的交互，直接删掉动效** —— 「最好的界面动效往往是无感的」

### 3.3 建议写入 `index.css` 的令牌（替换现有 3 档）

```css
@theme {
  /* —— 缓动曲线：入场 / 标准 / 出场 三分离 —— */
  --ease-entrance: cubic-bezier(0, 0, 0.38, 0.9);      /* 东西出现 */
  --ease-standard: cubic-bezier(0.2, 0, 0.38, 0.9);    /* 可见全程（修正现有误用） */
  --ease-exit:     cubic-bezier(0.2, 0, 1, 0.9);       /* 东西消失 */
  --ease-expressive: cubic-bezier(0.4, 0.14, 0.3, 1);  /* 仅关键时刻 */
  --ease-feedback: cubic-bezier(0.34, 1.56, 0.64, 1);  /* 用户操作回弹，节制使用 */

  /* —— 时长：微交互 → 大动作 —— */
  --dur-micro:  70ms;
  --dur-fade:   110ms;
  --dur-fast:   150ms;   /* 由 160 收敛到 Carbon 档位 */
  --dur-standard: 240ms; /* 由 220 收敛 */
  --dur-deliberate: 300ms;
  --dur-large:  400ms;

  /* —— 编排：stagger 递增步长 —— */
  --stagger-step: 40ms;
}
```

**必须同步修掉的一个 bug**：`index.css:252 / :278 / :520` 三处无限循环动画（busy-pulse、qs-pulse、step-pulse）现在用的是 ease-out 型曲线，造成「快冲慢回」。无限循环应改用 `linear` 或对称曲线，否则脉冲节奏永远不自然。

### 3.4 编排参数（新增，项目完全没有）

| 场景 | 步长 | 上限 | 说明 |
|---|---|---|---|
| 列表 / 卡片网格入场 | 30–60ms | 第 8 项后不再递增 | 否则用户等太久 |
| 列表 / 卡片网格出场 | 20ms | — | 出场必须比入场快 |
| hover 连锁（如头像组） | 按距离衰减 | — | 见 §4.3 |

> 来自 Emil Kowalski《7 Practical Animation Tips》：UI 动画一般应 **< 300ms**；入场用 `ease-out`（开头快 → 有响应感），**永远不要用 `ease-in`**（结尾才加速，与直觉相反）；内置 `ease-out` 太弱，要用自定义曲线。

## 四、组件改造清单

按「改动收益 / 实施成本」排序，P0 是收益最高、最该先做的。

### P0 · 编排与结构（解决「平」的根本）

#### P0-1 视图切换过渡
- **现状**：`App.tsx:459-466` 六视图硬切
- **方案**：进入视图用 `opacity 0→1` + `translateY(4px)→0`，160ms `--ease-entrance`；退出更快（100ms）。
- **注意**：只包裹内容区，不移除左栏/右栏，避免整屏闪烁。
- **参考**：[transitions.dev · Page side-by-side](https://transitions.dev/) → Forward / back page transition

#### P0-2 列表与卡片网格的入场编排
- **现状**：`BoardView.tsx:298` 看板卡、`HotView.tsx:786` 热点卡、`KnowledgeView.tsx:42` 目录树、`ObservabilityView.tsx:270` 日志行 —— 全部瞬时渲染
- **方案**：`opacity 0→1` + `translateY(6px)→0`，逐项 `--stagger-step` 递增，第 8 项后封顶；总时长不超过 400ms
- **关键**：**不要**用 `animation-delay` 硬编码，用单个 CSS 变量 `--i` + `calc(var(--i) * var(--stagger-step))`，列表虚拟滚动时才不会错乱
- **参考**：[transitions.dev · Texts reveal](https://transitions.dev/)（两行带 offset stagger 上升）、[transitions.dev · Spinning counter](https://transitions.dev/)

#### P0-3 弹窗进出场（含 origin-aware）
- **现状**：`ui.tsx:49` 的 `if (!open) return null` 硬切，遮罩 `bg-black/25` 硬出现。项目里唯一有进出场动画的浮层是 Toast，标准不统一
- **方案**：
  - 面板：`opacity 0→1` + `scale(0.96)→1`，240ms `--ease-entrance`；关闭走 Exit 曲线（加速离场，暗示「走远了」）
  - 遮罩：`opacity 0→1`，`--dur-fade`；关闭用 `--dur-fast`（比入场快）
  - **`scale(0)` 是错的** —— 元素像「凭空冒出来」。起始值用 **0.9 以上**（推荐 0.93–0.96），模拟真实物体「泄气也有形状」
  - `transform-origin` 必须跟随触发元素，而不是默认的 `center`
- **参考**：[transitions.dev · Modal open/close](https://transitions.dev/)（scale + fade + blur）、[Emil Kowalski · 不要从 scale(0) 开始](https://emilkowal.ski/ui/7-practical-animation-tips#2-dont-animate-from-scale0)

#### P0-4 Toast 升级
- **现状**：`index.css:344-362` + `:549-581` 已有 `qs-toast-in` 和堆叠（全项目完成度最高的动效），但**没有 blur、没有 scale**
- **方案**：在现有基础上补 `filter: blur(2px)→0` + `scale(0.97)→1`。blur 的用途是「弥合新旧状态之间的视觉缝隙」，纯 crossfade 会看出两个独立物体
- **参考**：[transitions.dev · Toast open/close](https://transitions.dev/)（rise + fade + blur + scale）

### P1 · 状态反馈（补上「操作已生效」这一类）

#### P1-1 看板卡片状态流转
- **现状**：卡片在列间移动（规划中 → 进行中 → 待确认 → 已完成）时无任何视觉确认
- **方案**：卡片进入新列时轻微 `scale(1)→1.02→1` 脉冲 + 边框瞬时高亮；被采纳/归档时用**成功勾绘制**（stroke-dasharray 描边）替代现在的直接消失
- **参考**：[transitions.dev · Success check](https://transitions.dev/)（带 blur + rotate 的成功勾）、[transitions.dev · Notification badge](https://transitions.dev/)（对角滑入 + 弹簧弹入）

#### P1-2 阶段进度的统一表现
- **现状**：`TaskDetailView.tsx:277-279` 进度线有 300ms 过渡，但 `BoardView.tsx:106-129` 的 flowbar 是静态色块 —— 同一个「阶段推进」语义两套标准
- **方案**：flowbar 对齐进度线的补间逻辑；正在进行的阶段用 `qs-step-current` 的呼吸环（但要先修 §3.3 的曲线误用）；阶段完成瞬间加一次勾选 morph
- **参考**：[GodUI · Stepper](https://godui.design/docs/components/layout/stepper)（spring 进度线 + 数字→勾 morph，项目调研已认定为「直接用」）、[Aceternity · Multi Step Loader](https://ui.aceternity.com/components/multi-step-loader)

#### P1-3 骨架 → 内容 reveal
- **现状**：`qs-pulse` 只有脉冲，数据到达后直接替换，没有交接
- **方案**：骨架淡出 + 内容错峰淡入，做 cross-fade 而非硬替换
- **参考**：[transitions.dev · Skeleton loader and reveal](https://transitions.dev/)（pulse → content cross-fade）

#### P1-4 统计数字补间
- **现状**：`ObservabilityView.tsx:219` 统计卡、`HotView` 计数（91 条多源热点、24H 精选）全是静态数字
- **方案**：数值变化时滚动到新值（数字卷轴式）。注意**只在数值真正变化时触发**，避免每次渲染都动
- **参考**：[transitions.dev · Spinning counter](https://transitions.dev/)（数字像卷轴一样滚到目标值）

#### P1-5 异步按钮三态
- **现状**：`Btn`（`ui.tsx:5`）有 loading 态，是项目完成度最高的交互件，但缺「成功」态
- **方案**：点击 → loading（旋转）→ 成功（旋转指示 morph 成勾）三态自动流转，用于「保存 / 生成 / 采纳 / 质检」
- **参考**：[Aceternity · Stateful Button](https://ui.aceternity.com/components/stateful-button)（规划表已选定）、[transitions.dev · Spinner to check morph](https://transitions.dev/)

### P2 · 微交互（细颗粒度，锦上添花）

| 编号 | 组件 | 现状 | 方案 | 参考 |
|---|---|---|---|---|
| P2-1 | 按钮按下 | `index.css:94` 仅 `translateY(0.5px)` | 加 `scale(0.97)` 按下反馈 | [Emil · Scale your buttons](https://emilkowal.ski/ui/7-practical-animation-tips#1-scale-your-buttons) |

| P2-10 | 输入校验失败 | 无 | 抖动 + 错误色（克制，1 次即止） | [transitions.dev · Error state shake](https://transitions.dev/) |

### 6.2 关于是否引入动画库

**现状**：项目**零动画库**（`framer-motion` / `motion` / `@react-spring` / `gsap` 全部未引入，pnpm-lock 也 0 命中），全部动效为原生 CSS + 1 处 `requestAnimationFrame`。

**建议**：**P0 / P1 / P2 全部可以用原生 CSS 完成，暂时不需要引入动画库。** 理由：
1. Tailwind v4 `@theme` 已就位，扩令牌 + 加 `.qs-*` 类即可，改动面可控
2. 只有少数场景（共享元素过渡、layoutId、弹簧物理）真正需要 `motion`；本项目里这类场景只有 P2-5（Tabs 滑动指示器）和 P2-3（头像组距离衰减）
3. 引入动画库会增加 bundle 与 React 19 兼容性验证成本（`motion` 兼容，但需实测）

**如果后续要引入**，推荐 `motion`（framer-motion 的继任者，React 19 兼容），且**只用于上述两个场景**。

### 6.3 命名与文件约定

延续项目现有做法：新建动效类统一用 `.qs-motion-*` 前缀，写在 `index.css` 现有 `.qs-*` 区块之后，不新建样式文件（保持「唯一样式源」的架构）。

## 七、红线、风险与边缘情况

### 7.1 必须守住的红线
1. **保持 Quiet Signal**：不加阴影（浮层除外）、不加渐变光晕、大结构直角、小控件 4px 圆角
2. **只动画 `transform` / `opacity` / `filter`** —— 禁止动画 `height` / `width` / `top` / `left`（GPU 合成层之外，会触发重排）。例外：已有的进度线 width 过渡可保留，但新代码一律用 `scaleX`
3. **重复高频交互不加动效**：Carbon 与 Emil 都明确强调 —— 一天看几百次的 hover 动效会变成干扰。侧栏导航项、列表行 hover 应保持当前的 `transition-colors` 不动

### 7.2 风险点
| 风险 | 说明 | 应对 |
|---|---|---|
| `prefers-reduced-motion` 兜底 | `index.css:286-294` 已有一条**全局** `animation/transition-duration: .01ms !important`，另有 3 处局部覆盖（`:452`、`:541`、`:577`） | 新增动效自动被这条兜底覆盖 ✅；但新增的 **JS 驱动**动效（如数字补间）不受 CSS 兜底保护，必须手动判断 `matchMedia('(prefers-reduced-motion: reduce)')` |
| `KnowledgeGraphView` 的 rAF 力导向循环 | `KnowledgeGraphView.tsx:438-449` 有自研物理模拟 + `ResizeObserver`；React 重渲染可能打断它 | 该视图**不要**加 React 驱动的入场动画，避免与 rAF 循环争抢 |
| 骨架屏抖动 | 列表 stagger 入场与骨架 pulse 同时进行会产生视觉噪音 | 骨架消失与内容入场串行，不并行 |
| 长列表性能 | 看板列可能有很多卡片 | stagger 第 8 项后封顶；超过 20 项的列表改用「只对首屏做入场」 |
| 字体 FOUT 放大动效瑕疵 | Google Fonts CDN 在国内可能回退宋体，字体跳变会让入场动画看起来更糟 | 建议同步做**自托管字体 + `preload`**（独立于本次动效工作，但强烈建议） |

### 7.3 验收清单（每条动效落地后自查）
- [ ] 时长是否落在预期档位？（微交互 70–120ms，其余 < 300ms）
- [ ] 入场用 `--ease-entrance` / 出场用 `--ease-exit`？有没有误用！
- [ ] 有没有出现 `scale(0)`？（应为 0.9+）
- [ ] 只动画了 `transform`/`opacity`/`filter`？
- [ ] 关掉动画（`prefers-reduced-motion`）后，信息是否仍完整可读？
- [ ] 这个交互用户一天会看到 10 次以上吗？会 → 删掉动效
- [ ] `transform-origin` 是否跟随触发元素？
