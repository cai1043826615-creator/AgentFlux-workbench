## 零、前提原则（用户确认 · 优先级最高，任何梯队都不得违反）

### 0.1 知识库是「信息基础」，热点只是「环境情报」

```
知识库（产品资料 / 品牌规范 / 案例）
   │  提供「产品事实」——决定产出内容讲什么
   ▼
任务的产出内容（文案 / 图片）

热点（平台规则 / 大促节点 / 品类趋势 / 竞品动态）
   └─ 只是「环境情报」——影响怎么说（合规、话术、时点），
      绝不决定「做什么产品」
```

**反例（必须避免）**：今天热榜是「内存条涨价」，就把内容产出改成内存条。
**已发生的实证错误**：现场任务 `#7` 就是由热点「Apple 发布首款折叠屏 iPhone Duo，$1,999」一键创建成的「电商新品上架」任务——产品主体来自热点，与真实业务无关。

**因此已确认的边界修订**（由梯队 3 落实）：

- **移除**「热点创建任务」能力（`daily-hot` spec 中该 requirement 需改写）
- 热点改为**只读情报面板**；若某个任务确实需要参考某条热点，由用户**手动关联为任务背景**（走既有内容隔离/注入通道），而不是由热点派生任务
- 热点永远不能成为产品品类/主体的来源

### 0.2 两套「覆盖率」必须区分命名（避免同名不同义）

用户原始表述里「关联资料覆盖率」出现在两处，实为两个不同指标，**实现时必须分开命名**：

| 名称 | 归属 | 定义 | 用途 |
| --- | --- | --- | --- |
| **文档使用率** | 知识库侧（梯队 2） | 被至少一个任务关联过的文档数 ÷ 已索引文档总数 | 衡量「知识库有多少在真正被用」 |
| **产出溯源率** | 任务侧（梯队 1） | 任务产出中可追溯到关联资料的事实项 ÷ 全部事实项 | 衡量「这次产出有多少有据可查」 |

### 0.3 板块独立性不得破坏

- 板块 B（知识库）与板块 A（工作流）**互相独立、互不阻塞**；唯一耦合点是「任务关联资料」
- 板块 B 数据域独立（`knowledge_docs` / `knowledge_links` / `knowledge_fts` / `knowledge_hot_cache` / `knowledge_meta` / `task_kb_refs`），不读写板块 A 业务表
- Vault **只读**：任何写/删/移动操作必须被拒绝
- 板块 B 异常/未连接时，板块 A 全部功能照常

### 0.4 工程约束

- 不引入重型运行时依赖（现有依赖：Fastify / React19 / Vite6 / node:sqlite，均不加库）
- 中文优先；UI 沿用 Quiet Signal 设计语言（近白/黑/紫信号/衬线 Display 标题、直角、4px 小控件、无默认阴影）
- 图表/图谱沿用**自绘 canvas/SVG**，不引图库

## 二、T1 · `quality-loop` —— 产出可信度闭环

### 目标

让「产出有没有依据」在界面上**可见、可追、可修**。这是最贴近钱与合规的一批。

### 条目

**B1 · 产出溯源标记 + 产出溯源率指标**

- 交付物（文案）中命中关联资料的事实项（规格数值、认证、电芯等）需**可视化标记为「已溯源」**
- 任务详情新增**产出溯源率**指标（定义见 §0.2）：`可溯源事实项 ÷ 全部事实项`
- 任务卡/详情在**未关联任何资料**时必须明确警示：`参数由模型生成，请人工核对`
- 依据（实测，见验收记录第四节）：不注入知识库时 LLM 会**自信地编造**规格——实测编造了 `20000mAh`（实为 10000）、`370g`（实为 198g）、`3C 认证`（实为 GB 31241）、`18 个月质保`（无）。这类错误在电商上架等于虚假宣传

技术落点建议：
- 溯源判定以**关联资料片段文本**为参照做事实项抽取与匹配（规格模式：数字+单位、认证编号、材质词），无需引入 NLP 依赖
- 结果随交付物一起持久化，供前端渲染标记

**B2 · 打回意见注入返工上下文**

- 现状缺陷：`reject(taskId, note)` 的 note 只写入 `task_events`，**返工时的 Agent 读不到** → 「打回」形同虚设，质量闭环断裂
- 要求：打回 note 走**与知识库资料同一条注入通道**（`SmartProducer` 的 system prompt 组装），并在任务详情展示「第 N 次返工 · 意见：…」

**B11 · 生图子任务重试（上限 3 次）+ failed 不计入待决策**

- 现状缺陷（已被 `docs/改动记录/02_验收记录-真实端到端_0910.md` 实证）：生图子任务 `failed` 后无单图重试/跳过，且 `allImagesDecided` 把 failed 当作「未决策」→ **拍板点永远推不动，任务卡死**
- 要求：
  - 单张图**自动重试，重复次数上限 3 次**（超过则标记为失败，不再重试）
  - provide **单张「重试」/「跳过」**操作
  - `failed` 图片不参与「是否全部已决策」的判定

### 验收标准（每项都要能实测）

1. 关联了产品资料的任务，其文案交付物中规格数字带「已溯源」标记；未关联资料的任务显示人工核对警示
2. 任务详情可见产出溯源率数值，且与人工核对结果一致
3. 打回时填写的意见，能在返工产出的 prompt 中被验证存在（注入到 producer 最终 system prompt），且任务详情可见返工次数与意见
4. 人为制造一次生图失败 → 自动重试至多 3 次；3 次仍失败则该图标记 failed，拍板点**仍可推进**（不卡死）
5. 后端测试全绿；前后端 typecheck + build 0 error

### 并行拆分建议

三个条目彼此独立，可 3 条子代理并行：B1（前后端 + 抽取算法）／B2（后端注入 + 前端展示）／B11（引擎 + 前端操作）。

## 三、T3 · `hot-intel` —— 热点情报层重构

### 3.1 边界修订（本梯队最重要，先做）

- **移除**：热点卡片上的「创建任务」按钮及其预填逻辑（`frontend/src/features/knowledge/HotView.tsx`、`App.tsx` 的 `openNewTask(prefill)`）
- **改写** `daily-hot` spec：删除「热点创建任务」requirement，替换为「热点作为任务背景（手动关联）」
- 新增能力：用户在任务详情/新建任务时，可把某条热点**手动挂为任务背景**（走既有注入通道，与知识库资料并列展示，标注来源为「外部环境情报」而非「产品事实」）
- 相关代码：`backend/src/knowledge/hot.ts`、`backend/src/knowledge/refs.ts`（或新增 `hot-refs`）、`backend/src/routes/knowledge.ts`

### 3.2 A4 · 热点卡片信息分层 + 排版重做

用户明确反馈：**当前热点页「太丑、可读性太差」**。参考「个人 AI 工作台」热点页（`http://127.0.0.1:5173/daily-hot`）的排版：

| 参考页做法 | 我们现状 | 要求 |
| --- | --- | --- |
| 顶部三枚统计药丸：多源热点 / 今日必看 / 24H 精选 | 一行纯文字「共 X 条 · 必看 X…」 | 改为药丸（bordered pill）形态 |
| 信息条：`AI 日报 2026-09-11 · 16 条 · 北京时间 08:00 发布` + 「打开日报 ↗」 | 只有「数据时间 / 缓存至」 | 补数据源新鲜度 + **上游日报外链** |
| 卡片带 `01/02/03` 序号 | 无 | 加序号 |
| 卡片带证据等级标签（`MULTI-SOURCE EVENT`）+ 领域标签 | 只有领域标签 | 加证据等级（多源事件 / 单源 / 可回查原文） |
| 卡片内容分两层：`讯息`（摘要）+ `最新进展` | 单层摘要 | **分层展示**，无进展则隐藏该层 |
| 三栏编辑式网格、衬线大标题 | 单栏卡片列表 | 大屏三栏 / 中屏两栏 / 窄屏单栏 |

同时必须保留并强化**降级三态**（live / stale / unavailable）的可读提示。

### 3.3 B10 · 多信息源接入（重点）

- 现状：只接 `https://aihot.virxact.com`（AI 行业聚合），与电商关注域交集很小
- 要求：接入**多源**，覆盖 平台规则 / 促销节点 / 品类趋势 / 竞品动态；每个源标注来源与证据等级；源可配置、可单独降级（单源失败不影响其他源）
- **源接入顺序（用户已确认，2026-09-11）**：**实现期先接公开源**——即调研报告中 P0/P1 里**无需凭据、无需企业资质**的源；报告中标注为「需企业资质/账号」或「合规风险高」的源（微博/知乎/抖音公共热榜、官方开放平台 API）**本期不接入**，作为后续增量（配置项 `sources[].enterpriseCredentialRequired` 已预留），**不阻塞本期开发**
- 具体候选源清单见调研报告：**`docs/设计/05_热点多信息源调研_0911.md`**（已产出：真实 HTTP 可达性实测 + 合规风险分级 + P0/P1/P2 优先级）
- **根因提示（调研结论，务必读）**：问题不是「源太少」，而是**「源领域」与「关注域」之间缺约束**——无权重、无作用域、无负向词的子串匹配，叠加 `sourceCount >= 2` 判必看，导致 AI 圈多信源跟进的热门科技新闻反而更容易进「今日必看」。**因此加源必须同时落地「源作用域 + 源权重（tierCap）」与降噪规则（§3.4），只加源不解决假阳性。**

### 3.4 降噪规则（我实测发现的假阳性）

- 现状：用电商关注域匹配 AI 行业源，`发布`/`预售`/`平台` 这类泛词导致 **Apple 发布会、DeepSeek 模型发布都被判成「竞品动态」进必看**
- 要求：关注域配置增加
  - **排除词**（命中则直接降级）
  - **多词命中要求**（同一条热点需命中 ≥2 个关键词才进该关注域，可配置）
  - **源权重**（非电商垂直源的条目默认不高于「浏览」层）

### 3.5 验收标准

1. 热点页不存在任何「创建任务」入口；从热点无法派生出产品任务
2. 任务详情支持手动关联热点作为背景，注入内容中该段明确标注为「外部环境情报」且与「产品事实」区分
3. 热点页视觉达到参考页水平：统计药丸 + 证据等级 + 序号 + 双层内容 + 响应式多栏；可读性经截图比对确认
4. 至少接入 2 个非 AI 行业的源；单源故障时其他源照常展示且标注降级
5. 实测噪音下降：同一批数据下，「必看」层不再出现与电商无关的条目（用固定样本回归验证）
6. `openspec validate hot-intel` 通过；后端测试全绿；typecheck + build 0 error

### 3.6 并行拆分建议

「边界修订」（3.1）必须先行且**单独提交**（它改的是既有能力语义）；之后 3.2 排版、3.3 多源、3.4 降噪可 3 路并行。

## 四、T2 · `knowledge-ux` —— 知识库页体验升级

### A1 · 顶部紧凑总览带（用户已选形态）

**不新增视图、不打断现有三栏浏览效率**，在知识库页顶部横向铺一条总览带：

- 统计卡：文档 / 标签 / 目录 / 关联边（复用已有 `knowledgeStats()`）
- **星图缩略预览**（复用现有 `KnowledgeGraphView` 的 canvas，缩小尺寸只读渲染；点击进入星图）
- 最近更新若干条
- 健康度摘要（见 A2）

### A2 · 知识健康度（缩小显示）

- **文档使用率**（定义见 §0.2）+ **孤岛文件数**（既无文档间链接、又无共享标签的文档）
- 以紧凑形式呈现（总览带内的小指标 + 星图工具栏的「N 页面 / M 双链 / K 孤岛」），**不新增大块面板**
- 孤岛文档需可**一键筛选列出**（与 A3 的过滤联动），因为孤岛 = Agent 永远检索不到的资料

### A3 · 星图交互提示 / 图例 / 缩放控件 / 过滤

- 页头补一句操作说明：「悬停看关系，点击聚焦邻居，双击进入文档」
- 工具栏补图例：「拖拽 · 滚轮缩放 · 双击阅读」
- 右下补缩放控件：百分比 + 放大 / 缩小 / 适配
- **过滤（图谱透镜）**：
  - 按**目录**
  - 按**标签**
  - 按**有链接 vs 孤岛**
  - 业务向预设：**「只看产品资料」「只看品牌规范」**（依据文档标签/目录预设，可配置）
- 双击节点 → 进入文档阅读（当前是单击进详情面板；两者都要保留）

### A5 · 空状态写「怎么用」

当前空态多为「暂无数据」「暂无图谱数据」。要求每个空态除说明「这里是什么」外，必须给**下一步该做什么**。参考写法：

> 「待看队列还是空的」+「在任意素材行点击『待看』，它会留在这里等你回来。」

覆盖清单（至少）：
- 知识库未连接 → 已具备（保留）
- 知识库已连接但无文档 / 无标签 / 无目录
- 星图无数据（无链接无标签）
- 搜索结果为空
- 热点不可用 / 无热点
- 「关联知识库资料」步骤无搜索结果

### 验收标准

1. 知识库页顶部出现总览带，三栏浏览功能与既有行为完全一致（回归不破）
2. 总览带可见文档/标签/目录/关联边 + 星图缩略图 + 文档使用率 + 孤岛数
3. 星图：操作说明、图例、缩放控件（含百分比）齐备；四种过滤可用，且「只看产品资料/只看品牌规范」按预设生效
4. 双击节点进入文档阅读；单击仍出节点详情
5. 上述 6 类空态均含「下一步该做什么」的指引文案
6. 前后端 typecheck + build 0 error；知识库未连接时板块 A 不受影响（独立性回归）

### 并行拆分建议

A1+A2（总览带与健康度，同属一个区域，建议同一子代理）／A3（星图）／A5（空态清单）→ 2-3 路并行。

## 六、交叉依赖与协调点

1. **「文档使用率」口径**（T1/T2 共用）：以本文 §0.2 的定义为准，实现时由 T1 先提供计算函数所在模块，T2 复用；若并行开发，按定义各自实现后统一。
2. **`task_kb_refs` 表**：T1（B1 溯源）、T4（B6 失效告警）都读它，**只读，不得改表结构**；如需扩展字段（如 `hot_refs`），由 T3 新建独立表，避免冲突。
3. **热点的两处使用**：T3 定义「热点挂为任务背景」的存储与注入；T1 的 B2 也要用同一条注入通道 → **注入通道的组装函数（`buildProducerSystemPrompt`）是共享改动点**，建议 T1 先改，T3 在其之上追加热点段。
4. **`daily-hot` spec 的语义变更**（T3）会影响 `openspec/changes/knowledge-base/specs/daily-hot/spec.md`：T3 应在自己的 change 内以 MODIFIED 表达，并在 T3 的 proposal 中说明与未归档的 knowledge-base 的关系。

## 七、执行方式（供后续对话遵循）

1. 每个梯队一个 OpenSpec change（已建好 proposal / specs / design / tasks），开工前用 `/openspec-apply-change <tier-change>` 读取任务
2. **少梯队、梯队内部多并行**：梯队内部的独立条目用 subagent 并行（各梯队已给出拆分建议），同一文件避免两个代理同时改
3. 每个条目完成即勾选 tasks；**不得跳过验收标准**，也不得把未验证项标为完成
4. 完成后按需归档；归档前校正文档与实现的一致性（本次已发现过的文档漂移问题）
5. 提交粒度：一个条目一次提交（中文 conventional commit），避免把多个条目混在一次提交里
