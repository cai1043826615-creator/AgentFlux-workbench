# 工作流技能「组件化」设计决策与实施建议（2026-09-16）

> 来源：2026-09-16 用户就「技能挂载与工作流隔离」的口径纠正 —— 原话：
> 「WORKFLOW_SKILLS 是整个系统的流程，为什么要让用户挂载，即使后面更新了其他的电商工作流流程，也应该作为组件按钮给客户选择」
>
> 本文档**取代** `技能挂载与工作流隔离优化建议-2026-09-14.md` 中与 `WORKFLOW_SKILLS` 相关的表述（该文建议一第 1 条「替代散落的 WORKFLOW_SKILLS 字符串硬编码」的方向已被本次决策否决）。
> 交接对象：下一个实施 agent。文件路径与函数名均经源码核实。

---

## 一、结论（口径已定）

| 概念 | 定位 | 谁来管 |
|---|---|---|
| **技能库 / 知识库文档** | 用户可以自由挂载的素材 | 用户在 Agent 配置里挂 |
| **工作流专属技能**（`WORKFLOW_SKILLS`） | **系统级流程组件**，代表「这条业务流必须遵守的红线」 | 系统维护，**不作为挂载素材要求用户自己挂** |

因此：

1. `WORKFLOW_SKILLS` 机制**保留**，继续由系统维护，**不并入用户挂载**。
2. 对用户侧的呈现方式，目标形态是**「组件按钮」**——把系统内置的工作流组件列出来，由用户**选用/开关**，而不是让用户去技能目录里翻文件手动挂。
3. 后续新增电商/小红书工作流时，其系统组件也按同一形态**自动出现在按钮列表里**，不需要用户做任何挂载动作。

## 二、现状（已核实 · 2026-09-16 实跑验证）

代码位置：`backend/src/agents/smart-producer.ts`

```ts
const WORKFLOW_SKILLS: Record<string, string[]> = {
  小红书合规违禁词清单: ['xhs-note'],
};
```

- 语义：`技能id → 适用的工作流id 列表`；workflowId 命中即注入 `【工作流专属技能】` 段。
- 注入点：`buildProducerSystemPrompt`，段序固定为 base → 【挂载技能】→【挂载文件】→【工作流专属技能】→【知识库资料】→【热点背景】→【返工意见】。
- 特性：**不占用 Agent 的个人技能位**，任何 Agent 跑该工作流都拿到（设计师、主管也拿到）。

### 已实测确认的两点（注入探针 30/30 断言通过）

1. **能正确注入**：`agent-copy × xhs-note`、`agent-design × xhs-note`、`agent-supervisor × xhs-note` 均含《小红书合规违禁词清单》，电商工作流均不含。
2. **与个人挂载重复时已去重**：美美的小红书份同时也挂了《小红书合规违禁词清单》，实测 prompt 中该内容**只出现一次**（本次已加 `excludeSkillIds` 排除清单）。

## 三、待实施：组件按钮形态

### 3.1 数据模型建议

现状 `WORKFLOW_SKILLS` 是「技能 → 工作流列表」的**硬编码反向索引**，不适合做按钮列表（要按工作流正查）。建议改为**按工作流正排的组件清单**：

```ts
/** 系统工作流组件：按工作流 id 正排，供 UI 直接渲染成按钮组 */
export const WORKFLOW_COMPONENTS: Record<string, { id: string; label: string; skillId: string; desc: string }[]> = {
  'xhs-note': [
    { id: 'xhs-compliance', label: '小红书合规红线', skillId: '小红书合规违禁词清单', desc: '绝对化用语/医疗功效/夸大用语禁区，全流程强制' },
  ],
  'ecom-new-listing': [],
};
```

由 `workflowSkillIdsFor(workflowId)` 从该表派生，保持注入侧单一来源。

### 3.2 是否允许用户关掉

这是需要在实施前拍板的语义点，二选一：

- **方案甲（建议）**：**只读展示**。组件在界面上以「已启用」按钮形式呈现（灰底、带「系统」标记、不可点掉），只用来**告知用户「这些红线是系统自带的，你不用挂」**。改动最小，风险最低，不破坏合规兜底。
- **方案乙**：**可开关**。需要新增存储（如 `settings.workflowComponents` 或 `agents` 侧开关），并且必须处理「用户关掉合规红线 → 合规失守」的风险。若采用，建议只对非合规类组件开放开关，合规类永久锁定。

**建议先落方案甲**，把「用户不用自己挂」这件事在界面上讲清楚；方案乙等有明确的「想关掉」诉求再做。

### 3.3 界面落点

| 界面 | 现状 | 期望 |
|---|---|---|
| Agent 配置弹窗「技能与文件」卡片 | 只有「电商行 / 小红书行 / 文件行」，全靠用户挂 | 每行下方增加「系统组件」只读区，列出该工作流的系统组件按钮 |
| 二级挂载弹窗 `SkillMountPicker` | 技能目录按分类过滤后供勾选 | 顶部或底部增加「系统组件（无需挂载）」说明区，避免用户到技能目录里重复挂 |
| 任务详情 / 内容交付页 | 无技能维度展示 | 可显示「本任务生效的系统组件」徽标（可选，非必须） |

涉及文件：
- `backend/src/agents/smart-producer.ts`（组件表 + 派生函数）
- `frontend/src/features/workstation/AgentSettingsModal.tsx`（系统组件只读区）
- `frontend/src/features/workstation/SkillMountPicker.tsx`（说明区）
- 若要暴露给前端，需经 `GET /api/agents/skills` 或新增 `GET /api/workflows/:id/components` 透出

### 3.4 验收要点

1. 电商工作流看不到小红书合规组件；小红书工作流能看到。
2. 系统组件不占用「已挂 N/M」计数，不与用户挂载列表混排。
3. `workflowSkillIdsFor` 派生的注入结果与改造前**完全一致**（回归 `backend/src/agents/__tests__/skill-workflow-isolation.test.ts`）。
4. 新增一条工作流并声明组件后，按钮**自动出现**，无需用户操作。

## 四、连带发现：新增工作流会串味（设计缺口）

**现象（已实测）**：给一个**未分份**的未来工作流（模拟新电商流 `future-new-listing`）组装 prompt 时，美美拿到的是**各份并集**——即电商两个文案技能**加上**《小红书合规违禁词清单》。小红书合规红线会串进新电商工作流。

**根因**：`buildSystemPrompt` 的读时兜底逻辑是「份缺失 → 回退全局 `skills`」，而全局 `skills` 现在被维护成**所有工作流的并集**（`PUT /api/agents/:id` 与 `ensure.ts` 都按并集重算）。于是：

- 旧数据（完全没有分份）→ 回退全局 = 应该的兼容行为；
- **新工作流（有分份、但没这个键）→ 也回退全局 = 拿到并集 = 串味**。

两种情况当前用的是同一条兜底路径，无法区分。

**建议修法**：区分「整行没有分份」与「有分份但缺这条工作流」：

```
works` 有内容（非空对象）但缺该 workflowId 键 → 视为「该工作流不挂任何个人技能」→ 返回 []
row.workflow_skills 为空对象/坏行            → 旧数据 → 回退全局 skills
```

这与本次已落地的「空数组是有效值」语义一致（见 `agent-mounts.ts` 注释）。修完后，新增工作流的默认状态是「个人技能为空、系统组件照常注入」，需要什么再让用户挂，语义可预期。

**注意**：此修改会让新工作流的行为**与当前不同**（从「继承并集」变为「空」）。是否接受需用户确认；若希望新工作流默认继承某组技能，应在组件表里显式声明，而不是靠并集兜底。
