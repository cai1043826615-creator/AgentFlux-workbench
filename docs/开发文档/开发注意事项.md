# 开发注意事项

> 汇总 multi-agent-ecom-workbench（多 Agent 电商新品上架工作台）开发对话中的注意事项与用户提醒，供后续开发与复盘参考。
> 维护：每个开发会话如涉及新的注意点，追加到对应小节；用户明确提醒的内容放在「一、用户提醒」并标注。

---

## 一、用户提醒（必须遵守）

### 1. API 密钥安全红线（最高优先级）
> 用户原话：「当用户在界面上填写 API 的时候，无论放在哪里都不能发送如上传 GitHub 这种严重的暴露行为」

- **UI 上填写的 API Key 绝不能进 GitHub**，无论填在哪个界面（Agent 设置 / 渠道配置等）。
- 落地措施：
  - `.gitignore` 补强：`*.pem *.key *.p12 *.pfx id_rsa id_ed25519 secrets* *credentials* *credential.json *service-account*.json .ssh/`，并忽略 `.env.local`、`backend/data/*.db*`、`backend/data/uploads/`。
  - 提交前强制扫描：`backend/scripts/check-secrets.mjs`（被 `.git/hooks/pre-commit` 调用），扫描 git 暂存区内容与文件名，命中 `sk-*` / `ghp_` / `AIza` / `AKIA` / `xox` / `Bearer` / 私钥块 / `key=赋值` 即阻止提交（exit 1）。
  - 扫描器放行：占位符（xxx/your/example/placeholder/`<...>`/`****`）与 `process.env.X` 环境变量引用（那是安全写法，不是硬编码密钥）。
- ⚠️ **钩子只装在本机 `.git/hooks`（不入库），换机需重装**；`check-secrets.mjs` 已入库可随仓库分发。
- 每次 `git add -A` 前肉眼核对 `git status --ignored`；真实密钥一律只写 `backend/.env.local`。

### 2. Agent 设置显示必须与实际运行一致
> 用户原话：「我的 api 和 agent 都正常使用，为什么在 agent 设置一直显示未配置」

- **「已配置」判定要与运行时一致**：面板 key 或 `.env` 默认渠道回退 = 后端权威 `isAgentConfigured(agentId)`；不能只看 DB 里存的 `baseUrl && apiKey`（DB 可能是历史遗留的空 key，实际运行时已回退 .env 正常）。
- 渠道判定规则：
  - `agent-design`（平平，生图）→ 生图渠道（IMAGE_* env 或面板 imageChannel）
  - `agent-supervisor`（波波，视觉审阅）→ 视觉渠道（SUPERVISOR_* env）或 LLM 渠道
  - 其余文本 Agent → LLM 渠道（DEEPSEEK_* env）
- 表单保存时**未填字段保留原值**（`apiKey: 输入.trim() || prev?.apiKey || ''`），防空串覆盖已有配置；未填 key 时提示「已配置：使用默认渠道密钥（在此填写可换成专属密钥）」，输入框占位「留空则使用默认渠道密钥」。

### 3. 生图必须基于参考图（关键缺陷）
> 用户原话：「上传的图片和生成的图片完全是2回事，证明没有把我上传的图片作为参考图提交，导致所有的图片产品全部不是一个，各生各的」

- **有上传参考图时，所有生图都必须基于它生成**；同时波波要检查一致性，**不一致直接打回重做**。
- 上传图很丑或没有 → 用**主图 1** 的图片来生成副图和详情图（策略：有图用图、无图用主图 1）。
- 后续所有图片都基于主图 1 确认产品一致性；出图与审阅工作流里这部分只需波波确认（先审），人工确认点保留。

### 4. 波波换能识图的 API + 增强审阅
> 用户要求：波波更换一个能够识图的 api，并增强她的审阅机制

- 波波视觉审阅渠道：`SUPERVISOR_BASE_URL=https://api.yhlxj.ai/v1` + `SUPERVISOR_API_KEY` + `SUPERVISOR_MODEL=gpt-5.5`（OpenAI 兼容，支持多模态图片输入）。
- 审阅机制：逐张对比「基准图（上传参考图，无则主图 1）vs 生成图」判断产品一致性；不一致 → issues 打回对应阶段（main-image / detail-image）返工；全部一致 → 放行，人工仍可确认。

### 5. 文档记录以会话实际为准
> 用户要求：盘点时以会话的内容为准再进行补充

- 写开发日志/注意事项等文档时，**以会话实际内容为准**，发现已有内容不符或有遗漏 → 修正补充，不得遗漏、不得编造。
- 填统计数字（总提交数、未推送数、按类型计数）前先跑 `git rev-list --count HEAD` / `git log origin/master..master` / 类型分组核对。

### 6. 文案术语统一
- 「归档」仅指任务归档动作；已归档列 → **已完成**、交付归档 → **交付完成**、待拍板 → **待确认**、拍板点 → **确认点**。
- 历史落地记录 / 归档 openspec 不追溯改写。

## 二、开发踩坑技术注意事项

### 1. 渠道必须「整组一致」选择
- 曾踩坑：`llm.ts` 用「DB 的 baseUrl + supervisor env 的 apiKey」字段级拼接 → `https://api.deepseek.com` 配上 yhlxj 的 key → **401 认证失败**。
- 正确做法：渠道按整套选择——设置面板 `llmChannels[agentId]` 配了专属 key → 整套用它；否则 supervisor 视觉渠道整套；否则默认 LLM 渠道整套。**严禁 baseUrl 与 apiKey 拆开拼**。

### 2. 参考图存储是路径不是 dataURL
- `tasks.reference_image` 存的是 `/uploads/xxx.jpg`（上传时 dataURL → 落盘文件 → 返回路径）。
- 提交生图 / 视觉审阅前必须**读本地文件转 dataURL**（`toDataUrl`：data: → 原样；`/uploads/xxx` → 读 `backend/data/uploads/` 转 base64；http(s) → 原样，若用于图生图会因无法解析退化为文生图）。
- 生成图（deliverables 里的 ImageItem.url）本身就是 dataURL，可直接用于视觉审阅。

### 3. 生图渠道的参考图协议
- 当前生图渠道（img-api.apinebula.ai / gpt-image-2）：`/images/generations` 带 `images` 数组参数 → **500 不支持**。
- 图生图必须走 `/images/edits`（multipart FormData：`model` / `prompt` / `image`(Blob) / `n` / `size`）。
- `/images/edits` 偶发 `ECONNRESET`/`UND_ERR_SOCKET`（网络抖动），重试可解。

### 4. 生图可靠性：重试 + 占位图纪律
- 真实渠道偶发抖动 / 上游限流 → **3 次重试 + 指数退避**（1500ms × attempt），失败打 warn 日志。
- 3 次都失败才标记 `status='failed'`；**绝不把 SVG 占位图当成品图入库**（占位图仅用于「生图渠道未配置」的 mock 降级）。

### 5. 视觉审阅判定需校准（防误打回死循环）
- gpt-5.5 对「同一产品」默认判定**过严**：白底图的光影、材质、纹理、构图差异都会被判为「不一致」→ 所有任务都会被打回。
- 判定标准应写清：「核心产品是否同一件——品类、颜色、造型、LOGO/标识、核心特征一致即视为同一件；角度、光线、背景、构图、渲染质感、材质细节差异不影响判定」。

### 6. 视觉审阅容错
- 单张检查失败 → `failed++` 跳过、打日志，不中断整轮（避免一次抖动毁掉整条链路）。
- 视觉渠道不可用（`LlmChannelUnavailableError`）→ 降级为原文本校对，流程不阻塞。
- 不一致 → `issues: [{ targetStage, note }]` → 上层 `reviewRollback` 打回对应阶段重做；一致 → `reviewPass` 放行（人工确认点仍在）。

### 7. 「已配置」判定与保存（见一.2）——补充实现细节
- 前端用后端返回的 `channelConfigured`（权威），不要在组件里自己 `baseUrl && apiKey` 算。
- WS `agent:status` 推送时保留原 `channelConfigured`（`{ ...a, ...msg.agent, channelConfigured: a.channelConfigured }`），防止被覆盖。

### 8. 运行时模型显示
- 波波实际用 gpt-5.5（SUPERVISOR_* env），但 `agents` 表 model 可能是旧值（deepseek-chat）→ 界面/执行日志会显示旧模型。
- 用 `effectiveModel(agentId, storedModel)` 做权威：supervisor 视觉渠道已配置时返回 `CHANNEL.supervisor.model`，其余返回存储 model。
- 历史 `agent_executions` 的 model 可一次性回填对齐。

### 9. pre-commit 密钥钩子
- 安装位置 `.git/hooks/pre-commit`（**不入库**），命令：`cd $(git rev-parse --show-toplevel) && node backend/scripts/check-secrets.mjs || exit 1`。
- 换机/克隆后需重新安装；脚本 `check-secrets.mjs` 已入库可分发。

### 10. 浏览器 / 脚本验证技巧
- DOM 定位别用宽泛的 `textContent.includes('美美') && includes('最近活跃')` 匹配 div——会命中**外层大容器**，`querySelectorAll('button')` 第一个「设置」会点到左栏设置而不是 Agent 卡设置；应精确到 `section` 卡片（如 `includes('产品文案专家')`）再找按钮。
- MCP 真实点击优先用 a11y 快照的 uid；程序化 `dispatchEvent(MouseEvent)` 可触发 React 合成事件（真实 CDP click 偶发落点偏差）。
- PowerShell 发中文 JSON body：必须 `[System.Text.Encoding]::UTF8.GetBytes($body)` + `ContentType 'application/json; charset=utf-8'`，否则服务端 `imageId`（中文名）匹配不到，approve 静默不生效。
- 图片阶段全流程（7 张视觉审阅）1-3 分钟，客户端超时（HttpClient.Timeout）需调大到 ≥280s。
- 生图单请求 180s 超时、LLM 120s 超时（AbortController）。

### 11. 共享工作区协作
- 仓库有多会话并行工作：**`git add -A` 会混入别的会话的文件** → 提交前只 `git add` 本任务文件，核对 `git status --short`（第一列=暂存，第二列=工作区）。
- **不代推别人未完成的提交**；push 前先 `git fetch` 防冲突；本地领先（未推送）在日志中标 ⏳未推送。
- 不擅自处理别的会话的工作区内容（未提交删除、未跟踪文件、`.git-backup-*` 备份目录等）。

### 12. 参考图链路与一致性基准
- `resolveReferenceImage(task, isMain)`：有上传参考图 → 用它（主图/详情图都基于它）；无 → 主图纯文生图、详情图以已产出的**主图 1** 为基准。
- 审阅基准 = 上传参考图（有）或主图 1（无）；报告注明「基准：上传参考图 / 主图 1」。

## 三、性能与超时基线（实测）

| 项 | 实测 |
|---|---|
| 生图 edits 单张 | 2-3 MB dataURL（PNG） |
| gpt-5.5 双图视觉请求 | 基准 2.3MB + 目标 2.2MB ≈ 4.5MB 请求体，实测 200 正常 |
| 视觉审阅 7 张 | 全程约 1 分 12 秒 ~ 2 分 28 秒（逐张 10-20s） |
| 4 路并发 edits 压测 | 全部成功（非并发限制；偶发单路抖动靠重试） |
| 纯文生图 | 约 1-2s 出图（gpt-image-2） |
