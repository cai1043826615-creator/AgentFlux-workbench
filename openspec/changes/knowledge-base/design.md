## Context

在已完整落地的多 Agent 电商工作台（板块 A：frontend/ + backend/ + packages/shared/，Fastify + SQLite + WebSocket，Quiet Signal UI）旁，新增知识库管理系统（板块 B）。板块 B 与板块 A **互相独立、互不阻塞**，唯一耦合点是「任务关联资料」（见 specs/workflow-context）。板块 B 参考 person_dashboard（本地 01-0908-工作台 与 GitHub oyorf/person_dashboard）的 Vault 接入、每日热点与知识星图思路，但只复用思路与数据协议，不复用其含个人数据解析逻辑的 3000 行实现。见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**
- 板块 B 数据域独立（独立表），不触碰板块 A 状态机与既有表；未配置/异常时板块 A 照常运行
- Vault 只读接入 + 索引范围限定（白名单/排除目录），中文全文可搜（FTS5 trigram）
- 知识星图、每日热点（电商化关注域 + 缓存降级）作为板块 B 独立视图
- 唯一耦合点 workflow-context：新建任务勾选资料（可到章节/片段），Agent 执行注入，缺失降级
- 板块 B 内部重活（索引重建/热点抓取）异步，不阻塞任务推进

**Non-Goals:**
- 不做 v2 的 RAG 向量检索/自动注入（本次明确不做，作为后续边界）
- 不做交付物自动回写 Vault（坑1：留 Open Question，倾向 v2）
- 不做多 Vault 并行、跨设备同步、账号体系
- 不引入重型图库/分词库/电子表格库等额外运行时依赖

## Decisions

### D1. 数据域：与板块 A 同库、独立表域
知识库索引使用独立表：`knowledge_docs`（路径/标题/目录/标签/正文摘要/hash/mtime）、`knowledge_links`（文档间链接与共享标签关系边）、`knowledge_hot_cache`（热点缓存）、`task_kb_refs`（任务关联资料，跨板块唯一耦合点）。与工作流表同库（一个 SQLite 文件，事务与部署简单），但**表域完全隔离**，板块 B 代码不得读写板块 A 表，反之亦然。
- **理由**：单文件部署 + 板块间物理隔离；索引可再生（删除重建无损）
- **备选**：独立 DB 文件（隔离更强但跨库查询/事务繁琐）；内存索引（重启丢失，不可再生）

### D2. Vault 接入：设置面板 + 环境变量兜底
Vault 根路径存设置表（复用现有 settings 路由），环境变量 `WORKBENCH_VAULT_ROOT` 兜底；支持**目录白名单 + 排除目录**双配置（坑5：不全盘托出）。扫描器解析 frontmatter（title/tags），排除 `.git`/`.obsidian`/`node_modules` 等，只读操作由统一文件访问层封装（防越权写入）。
- **理由**：工作台已有设置面板，与 person_dashboard 的环境变量方式兼容
- **备选**：仅环境变量（无 UI，配置不直观）

### D3. 中文全文检索：SQLite FTS5 `trigram` tokenizer
`knowledge_docs` 正文建 FTS5 虚拟表（trigram），中文无需分词器即可按 3-gram 匹配（坑3）；对 1-2 字短词用 `LIKE` 兜底。better-sqlite3 自带 FTS5，零新增依赖。
- **理由**：零依赖、够用、实现期即可验证中文命中；为 v2 RAG 打基础（先解决「搜得准」）
- **备选**：jieba 分词 + 倒排（依赖重、维护成本）；FTS5 默认 tokenizer（中文按整句切分，搜不准——正是坑3）

### D4. 知识星图：链接/标签关系 + 轻量自绘渲染
图谱边来源：Markdown `[[wiki链接]]`/相对路径链接（入 `knowledge_links`）+ 共享标签。前端用自绘 canvas/SVG 力导向布局渲染（节点按文档/标签区分、缩放拖拽、悬停详情、点击跳转原文、关键词定位高亮）。
- **理由**：个人 Vault 规模小（数百文档量级），自绘可控 Quiet Signal 风格与性能；不引重型图库
- **备选**：d3-force / react-force-graph（依赖重、风格难统一）；移植 person_dashboard graph-engine（canvas 复杂且耦合其个人数据，移植成本高）

### D5. 每日热点：公共匿名 API + 电商化关注域 + 缓存降级
复用 person_dashboard 的 ai-hot 思路：公共匿名热点 API + 关注域配置（本地 `backend/config/attention.json`，不入版本库）+ 15 分钟 TTL 缓存（`knowledge_hot_cache`）+ 超时/失败降级。**默认关注域电商化**（坑2：品类趋势/平台规则/竞品动态/促销节点），而非其默认的 AI 行业关注域。热点卡片提供「创建任务」→ 预填新建任务表单（人工确认后进入板块 A）。
- **理由**：公共 API 零鉴权零成本；配置本地化可个性化
- **备选**：自建爬虫（合规风险）；平台开放 API（需授权、超 scope）

### D6. 任务关联资料（唯一耦合点）实现
- **选择**：新建任务弹窗增加「关联知识库资料」步骤，搜索知识库勾选文档/片段（最多 6 份），存 `task_kb_refs`（task_id, doc_path, anchor, note）；任务详情展示关联并可跳转原文
- **片段粒度**（坑4）：解析 Markdown 标题层级生成锚点，片段 = 标题到下一同级标题；v1 支持整篇或按章节，存「路径+章节标题」而非字节偏移（文档改版锚点漂移时降级为整篇注入并标记）
- **注入**：复用既有 skills/files 注入通道——service.ts 阶段执行前读取 `task_kb_refs` → 加载片段 → 并入 producer 上下文；资料缺失时以「资料缺失」提示降级，任务照常
- **独立性**：知识库未连接 → `task_kb_refs` 为空 → 注入跳过，新建任务与既有行为完全一致

### D7. 前端板块入口与页面
左栏分区顺序为「知识库 → 工作流 → 通用」（知识库置于最上），知识库分区含三个视图：知识库总览/浏览/搜索、知识星图、每日热点（`frontend/src/features/knowledge/`），复用 App.tsx 现有 view 状态机扩展；视觉沿用 Quiet Signal（近白/黑/紫信号/衬线 Display 标题），不引重型组件库。
折叠态图标列与展开态**逐项一一对应**（不为每个分区只留一个入口）：知识库 / 知识星图 / 每日热点 / 电商工作流 / 直播带货上架（置灰占位）/ 跨境选品（置灰占位）/ Agent 状态 / 设置。为消除折叠态的图标歧义，新增两个几何图标：`graph`（知识星图，节点网络）与 `trend`（每日热点，趋势折线），展开态同步使用，保证同一选项在两种状态下图标一致。
- **理由**：与既有左栏折叠分区形态一致；折叠态信息密度与展开态对齐，避免折叠后丢失入口或认错图标；三个视图共享知识库 feature 目录，互不侵入板块 A 页面

## Risks / Trade-offs

- [FTS5 trigram 对 1-2 字短词匹配弱] → 短词 LIKE 兜底 + 搜索 UI 提示使用 ≥2 字词
- [索引与 Vault 实际文件漂移（用户经 Obsidian 改动）] → 启动时自动重建 + 手动「重建索引」按钮；v1 不做实时文件监听
- [大 Vault 全量扫描阻塞请求] → 索引重建后台任务，接口返回进行中状态，前端轮询/完成后通知
- [热点公共 API 来源不稳/频控] → 缓存 + 超时 + 降级提示；不承诺实时
- [Vault 只读边界被破坏] → 文件访问统一封装 + 只读测试 + 代码审查约束
- [关联片段锚点漂移] → 存「路径+章节标题」，匹配失败降级整篇注入并标记失效
- [同库表增长] → 知识库索引表可再生可清理；热点缓存有 TTL

## Migration Plan

- 全新数据域，无既有数据迁移；首版建表即用（幂等 ensureSchema 模式，与板块 A 一致）
- 回滚：板块 B 独立，整体回退不影响板块 A；SQLite 文件可备份恢复

## Open Questions

- **交付物沉淀回写 Vault（坑1）**：任务完成后把交付物（最终文案/图片）写回 Vault 指定目录，形成「知识库→注入→产出→沉淀」闭环。涉及板块 B 写能力，与「互相独立」需权衡（建议作为可选写能力、异步、失败不阻塞板块 A）。倾向 v2 与 RAG 一起做
- **热点数据源的电商垂直化**：实现期已确认公共匿名 API 为 `https://aihot.virxact.com`（零鉴权，`/api/v1/hot-topics` + `/api/v1/items`），但该源聚合的是 AI 行业资讯，与电商关注域只有部分交集——当前实现以电商化关注域过滤分层，未命中的内容归入「其他」。若需要真正的电商/品类热点，后续可换或并行接入电商垂直源（配置项 `sourceBaseUrl` 已支持，但仍需确认可长期稳定使用的公共源）
- **工作台内置资料库形态**：除 Obsidian Vault 外，是否还需要「工作台自带资料目录」（非 Obsidian 用户把资料直接放进工作台管理的目录）
