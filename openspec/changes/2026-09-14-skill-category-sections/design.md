## Context

见 proposal.md「Why」。改造对象的当前状态（已实读源码确认）：

1. `packages/shared/src/types.ts` 的 `AgentSkillInfo` **已定义** `category?: string`，但从未被真正赋值。
2. `backend/src/agents/skills.ts` 的 `parseSkillMeta(id, content)` 把它**硬编码为 `'文案'`**；`listSkills()` 只 `readdir(SKILLS_DIR)` 一层，不递归。
3. `backend/src/agents/skills.ts` 的 `readSkillContent(skillId)` 是**扁平查找**：`readFile(join(SKILLS_DIR, skillId + '.md'))`。**这是本次改造最大的风险点**——一旦把技能文件移入子目录，该函数立即失效，所有技能注入静默变成空串（`.catch(() => '')` 会吞掉 ENOENT），表现为「功能还在但技能不生效」，是典型的静默退化。
4. `backend/src/agents/smart-producer.ts` 的 `WORKFLOW_SKILLS` 已实现**按 workflowId 注入工作流专属技能**（`小红书合规违禁词清单` → `['xhs-note']`），因此「分区只是视觉」不成立：小红书的按域过滤已存在，本轮只需把分区做出来对齐它，不重复建设。
5. `backend/src/db/seed.ts` 预置 7 项挂载，实际目录仅 2 技能 + 2 文件，其余读取返回空串而 UI 仍显示已挂载。**用户决策（2026-09-14）：幽灵挂载实体化而非删除**——源材料优先取自外部技能库 `D:\AI\workbuddy\2026-09-12-16-27-36\2026-09-12-xiaohongshu-skills\skills`（100+ 个 SKILL.md，英文 kebab-case 目录 + frontmatter 格式），经核对无 seed 项同名技能，但 3 项有可提炼源材料（`03-数据分析/keyword-analysis`、`05-平台规则/content-review`、`01-内容创作/cover-design`），其余原创补齐。
6. `frontend/src/features/workstation/AgentSettingsModal.tsx` 挂载面板技能区为 `catalog.map(...)` 扁平渲染，未读取 `category`。

约束：`agents.skills` 列存的是技能**展示名**（如 `电商文案模板`），不是路径或 id；`skillMounted()` 同时匹配 `id` 与 `name`。这决定了目录结构可以变，但**技能 id（= 文件名去扩展名）必须保持不变**。

## Goals / Non-Goals

**Goals:**

- 让「技能属于哪条业务线」在数据层与 UI 层都可表达、可展示。
- 保持**技能 id 语义不变**，从而 `agents.skills` 无需任何数据迁移。
- 让失效挂载可见，消除「UI 显示已挂载、实际注入为空」的静默退化。
- 让 `readSkillContent` 从「扁平查找」改为「目录感知查找」，且对旧的平铺结构保持兼容。

**Non-Goals:**

- 不重做技能注入的分域过滤逻辑（`WORKFLOW_SKILLS` 已存在且工作流级过滤已生效）。
- 不引入多分类模型（`category` 保持单值）。
- 不改文件（FILES）区结构与上传链路。
- 不做技能内容在线编辑、不做技能版本管理。

## Decisions

### D1：分类来源 = 「目录即分类」，文件头可覆盖（而非纯元数据或硬编码映射表）

**决策**：分类由技能文件所在子目录决定（`backend/skills/ecommerce/` → 电商），技能文件头部的 `> 分类：xxx` 可覆盖目录值，未识别值原样保留。

**理由**：

- 纯元数据方案（只靠 `> 分类：`）要求每个技能作者都记得写，漏写即无分类，且分类事实只存在于文件内容里，目录浏览时不可见。
- 硬编码映射表方案（代码里维护 `{'电商文案模板':'电商'}`）每加一个技能都要改代码，是最容易腐坏的一种。
- 目录方案让「加一个技能」退化为「把文件丢进对应目录」，零代码；同时目录树本身就是分类文档。文件头覆盖用于处理例外（文件放在 xhs 目录但实质是通用能力），避免为了一个例外破坏目录整洁。

**备选与否决**：考虑过把分类写进 `.openspec` 风格的集中清单文件，否决——多一处需要与目录同步的真相来源，反而增加不一致风险。

### D2：保留「通用」区作为兜底，且未知分类不强行归并

**决策**：分区固定为 `电商 / 小红书 / 通用` 三个展示位；根目录平铺的 `.md` 归入「通用」；声明了未识别分类的技能**按原值展示**（排在已知分区之后），不归并进「通用」。

**理由**：「电商」（业务域）与「小红书」（渠道）不是正交维度，强行要求二选一会逼出错误归类。留「通用」兜底后，未标注分类的旧技能自然落入通用区，而不是从界面上消失。未知分类保留原值，是为了让问题**可见**——若把它静默塞进「通用」，作者永远不会发现自己写错了分类名。

**代价**：出现第 4 个分区时排序需有确定性规则（见 D4）。

### D3：`readSkillContent` 改为「目录感知 + 缓存索引」，而非保留扁平查找

**决策**：`listSkills` 扫描时构建 `id → 绝对路径` 的索引并缓存，`readSkillContent(id)` 先查索引；索引未命中再回退到根目录扁平查找（兼容直调未扫描的场景）。

**理由**：扁平查找在子目录结构下必然失败，且失败被 `.catch(() => '')` 掩盖成空串——这是「改了目录、功能悄悄失效」的典型陷阱。用索引一次扫描解决「重名歧义」与「查找成本」，同时回退路径保证任何先扫描后读取之外的调用方式不炸。

**备选与否决**：考虑过 `readSkillContent` 每次自行递归 `findFile`，否决——每个技能读取都要遍历目录，且加重名时结果不确定。

### D4：跨目录同名技能 —— 跳过并告警，不静默取先命中者

**决策**：扫描时发现两个目录下存在同名 `.md`（同 id），保留先扫描到的，跳过后者并 `console.warn` 输出被忽略的完整路径。

**理由**：id 重名会让「已挂载数据按 name 匹配」指向不确定的技能，属于会产出错误结果的静默 bug。告警让问题在启动日志里可发现。

**备选与否决**：考虑过直接用目录名限定 id（如 `ecommerce/电商文案模板`），否决——那会改变技能 id 语义，导致所有已存挂载数据失效，与 D5 冲突。

### D5：技能 id 与文件名保持不变，以「零数据迁移」为硬约束

**决策**：只移动文件目录位置，不改文件名，不改 `agents.skills` 存储格式（继续存展示名）。

**理由**：`skillMounted()` 已同时匹配 `id` 与 `name`，且存的是展示名，因此保持文件名即可让所有历史挂载继续生效。任何改变 id 语义的方案都会触发数据迁移，而迁移 SQLite 里 JSON 数组字符串的成本与风险远高于本改造的收益。

### D6：失效挂载在前端标记，而非后端过滤

**决策**：拉取目录后在**前端**比对，挂载项查不到即标红「已失效」；后端不静默剔除失效项。

**理由**：后端静默剔除会让用户「莫名少了一个技能」而无从得知；显式标记让用户看到问题并自行移除。与既有 `fileError` 的降级提示风格一致。

### D7：幽灵挂载 = 实体化补齐（而非删除），源材料优先复用外部技能库

**决策**：seed 的 7 项挂载全部落为真实文件——`SEO 关键词` / `质检清单` / `电商视觉规范` 从外部技能库的 `keyword-analysis` / `content-review` / `cover-design` 提炼成项目技能格式（`# 标题` + `> 描述：` + `> 分类：`，精简到 2–4KB 并注明来源）；`知识库整理` / `素材结构化` / `品牌手册` / `品牌视觉规范` 原创撰写。两个品牌文件以 `.md` 进 `backend/files/`（`.pdf` 不在挂载白名单，内容型挂载统一用文本承载），并由 `ensure.ts` 幂等迁移把存量库 `agents.files` 里的 `.pdf` 引用替换为 `.md`。

**理由**：删除方案会让用户看到「挂载凭空少了 5 个」且技能库始终是空壳；实体化方案里**新文件名与存量库已挂的名字严格一致**，存量库的技能挂载零迁移即生效，只有 `.pdf` 文件挂载需要一次幂等迁移——这是打通「技能库 → Agent」成本最低的路径。

**备选与否决**：整库导入 100+ 个 SKILL.md——否决，体积大、英文 frontmatter 与项目元数据约定不符、会把技能目录变成噪音场；直接拷贝 SKILL.md 改名——否决，长度 8–40KB 的技能全文注入 system prompt 会挤爆上下文预算，提炼成 2–4KB 精简版才符合「注入 prompt」的真实消费方式。

### D8：存量库的文件挂载迁移放在 `ensure.ts`，而非 seed

**决策**：pdf→md 的存量修正以幂等迁移步骤写进 `db/ensure.ts`（既有 `tasks.brief` 列迁移同款机制），`seed.ts` 保持「不存在才 INSERT」语义不变。

**理由**：seed 只影响新建库；存量库的修正必须走启动迁移。两者职责不同：seed 负责「初始该是什么样」，ensure 负责「从任意旧版本升级到当前该是什么样」。

## Risks / Trade-offs

- **[技能注入静默失效]** → 最大风险。`readSkillContent` 依赖扁平路径，移动文件后若不改该函数，所有技能注入会**静默变空**（无报错、无日志）。缓解：D3 的索引 + 回退；tasks.md 中单列一条「改造前后同一 Agent 的 system prompt 逐字一致」的回归验证，而非只测「技能列表能列出」。
- **[`listSkills` 变递归后 IO 放大]** → 每个技能仍被全文读取用于解析标题/描述（既有行为）。技能增多后扫描变慢。缓解：本轮改为**只读文件头部若干 KB** 再解析元数据（元数据约定在文件首部），避免读整个技能全文。
- **[实体化技能的质量与体积]** → 提炼/原创的 5 个技能 + 2 个品牌文件质量取决于撰写水平，过长会挤爆 prompt 上下文预算。缓解：统一约束在 2–4KB、结构化条目式（清单/公式/规范条目），并在文件头注明来源（提炼自外部技能库或原创），便于后续迭代；注入侧 `buildSystemPrompt` 不改，体积由文件本身控制。
- **[ensure.ts 迁移写坏 agents.files]** → 迁移会改写存量库 JSON。缓解：仅对**精确匹配** `品牌手册.pdf` / `品牌视觉规范.pdf` 的数组元素做替换，其余元素原样保留；JSON.parse 失败的行跳过不动（保持既有容错语义）；迁移幂等（已替换则无操作）。
- **[分类维度被误读为正交]** → 后续想加「爆款标题公式」这类跨域技能时会困惑。缓解：Proposal 非目标 + D2 明确「预留通用兜底」，并在技能文件头注释中示意 `> 分类：` 的语义。
- **[模块级缓存导致新加技能不刷新]** → 若索引在模块加载时构建并永久缓存，运行中新增技能文件不会出现。缓解：缓存仅在首次调用时构建（懒加载），或提供显式失效；本轮采用「懒加载 + 进程内缓存」，因为技能文件变更属于开发期行为，重启是既有预期。

## Migration Plan

1. 先改后端（`skills.ts` 的索引与查找、`parseSkillMeta`、`listSkills`），**此时目录尚未移动**，扁平结构走「根目录 → 通用」兼容分支，行为应与改造前一致（回归点 1）。
2. 移动两个技能文件到 `ecommerce/`、`xhs/`，建立 `common/`；实体化 5 个技能 + 2 个品牌文件落位。验证技能目录返回 7 条且分类正确、`readSkillContent` 仍能取到全文（回归点 2：既有技能 system prompt 逐字一致）。
3. `ensure.ts` 幂等迁移 pdf→md；`seed.ts` 挂载全集更新（新建库直接挂全套）。
4. 改前端分区渲染与失效标记（纯展示层，可独立回滚）。

**回滚**：本改造对库结构零变更（ensure 迁移只改 `agents.files` 的 JSON 值且幂等可逆）。回滚 = 把技能文件移回根目录 + 还原 `skills.ts` / `AgentSettingsModal.tsx` / `seed.ts` / `ensure.ts`；实体化新增的技能文件留在目录中不影响旧行为（旧代码只扫根目录）。
