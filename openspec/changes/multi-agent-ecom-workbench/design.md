## Context

全新项目：多 Agent 协同电商工作流 Web 工作台（见 proposal.md — Why）。**UI 方向已由用户最终确认**：低保真线框用灰白线框风（可交互版已定稿，`2026-09-08-电商新品上架工作流设计/低保真线框-可交互版-多Agent电商工作台.html`，左右等宽内容交付页已按用户要求实现）；**实际开发阶段的 UI 采用 Quiet Signal 设计语言**（近白画布 + 黑色信息层级 + 衬线 Display 标题 + 有限紫色信号色 + 大结构直角/小控件 4px + 无阴影，依据 quiet-signal-design skill 的 SPEC.md）。三栏布局（顶部全局栏 + 可折叠左侧栏 + 可折叠右侧聊天窗口）。工作流已确认：电商新品上架 6 阶段，2 个人工拍板点。当前目录无既有代码耦合，技术栈可自由选择。约束：Agent 需独立配置模型、按 Agent 隔离内容（人设/skill/文件/上下文），产出物需在工作台内预览与逐项审批。

## Goals / Non-Goals

**Goals:**
- 定义前后端分层与模块边界，使 7 个 capability（shell-layout / workstation / task-board / workflow-engine / chat / content-delivery / agent-observability）可独立演进
- 工作流引擎以「图定义 + 状态机执行」为核心：节点/边/条件分支描述流程拓扑，驱动看板 4 列流转、拍板点阻塞、主管校对回退
- 阶段内并行执行：主图/详情图多图生成按渠道分组并行、组内串行防限流，逐张即时上报进度
- Agent 执行与工作台解耦：Agent 跑在宿主侧，通过事件上报状态，前端只消费状态
- Agent 执行全程可观测：执行日志 + 统计（成功率/平均耗时）在工位与统计视图呈现
- 内容交付（文案/图片）原生可预览、可逐项采纳/打回

**Non-Goals:**
- 不做多工作流并行运行时的横向扩展设计（电商工作流 v1 单工作流）
- 不做真实的 LLM 调用协议细节、图片生成模型选型（属实现阶段）
- 不做多租户/账号体系（先单人使用）
- 不做移动端适配（v1 面向宽屏桌面端）

## Decisions

### D1. 技术栈：前端 React + TypeScript + Vite + Tailwind CSS，后端 Node.js（Fastify）+ TypeScript，存储 SQLite

- **理由**：全 TypeScript 单一语言栈降低心智负担；SQLite 零运维、单文件、事务可靠，适合 v1 单人/小团队规模；Fastify 轻量且生态成熟；Tailwind CSS 提供原子化样式底座，便于落地 Quiet Signal 设计令牌并适度借鉴 Aceternity UI / shadcn 风格组件（用户已确认 2026-09-08）。
- **备选**：Next.js 全栈（耦合过重，本产品是实时工作台非内容站）、Python FastAPI（需要双语言栈）、PostgreSQL（v1 过重，后续可迁移，SQLite 用 Drizzle ORM 保持迁移路径）。

### D2. 工作流引擎：图定义 + 状态机执行（StateGraph 式），事件溯源式状态更新

- 工作流以图表达：6 阶段为节点，边定义执行顺序；拍板点（卖点文案/主图）与主管校对的通过/打回为**条件分支边**；阶段节点可声明**并行子任务分组**。图定义序列化存入 `workflows.stages_json`（v1 预置「电商新品上架」图）。
- 每个任务持有 `workflow_stage`（当前节点）+ `board_column`（4 列）双字段。拍板点节点完成时进入 `待确认`；采纳 → 沿 approved 边推进下一节点；打回 → 沿 rejected 边回当前节点返工；校对不通过 → 沿 rollback 边回退到受影响节点。
- 状态迁移只由事件触发（`STAGE_COMPLETED` / `APPROVED` / `REJECTED` / `REVIEW_PASSED` / `REVIEW_ROLLBACK` / `SUB_TASK_COMPLETE`），每个事件写入任务事件日志（活动日志页由此直接渲染）。
- **理由**：流程拓扑显式可见（任务状态栏的流程预览直接渲染图定义）、分支与回退的扩展无需改引擎、与并行子任务天然衔接；事件溯源保留可回放、可审计（主管校对回退需要追溯）、活动日志与群聊通知天然同源。
- **备选**：简单 if/else 流转（回退与多轮重工场景下状态难以维护）；BPMN 引擎（v1 过度设计）；图定义仅用于展示而流转仍写死（失去编排价值）。

### D3. Agent 运行时：宿主侧 Worker 进程 + 事件上报，与前端弱耦合

- 每个 Agent 一个 Worker，读自己隔离的 `persona + skills + files`（内容隔离在宿主侧实施），配置独立模型。
- Worker 执行时通过消息总线（Node EventEmitter / 简单 WebSocket 广播）上报进度、完成、需审批等事件。
- **理由**：Agent 内容隔离天然物理边界；模型独立配置在 Worker 启动参数；前端不直接持有 Agent 上下文，只显示状态。
- **备选**：前端直接调 LLM（隔离与模型配置都难做）；全量服务端单体调度（v1 复杂度可控但耦合）。

### D4. 实时通信：WebSocket 推送（看板状态 / 聊天 / 审批弹窗）

- 看板、任务状态栏、工位在线状态、聊天、右下角审批弹窗均通过同一 WS 通道推送事件。
- **理由**：Agent 在后台运行，前端需被动感知状态变化（如「文案Agent 在写 20m」、任务进入待确认）。
- **备选**：轮询（简单但延迟高、浪费资源；聊天体验差）。

### D5. 数据模型（核心表）

- `agents`（id, name, role, persona, model, skills[], files[], online_status）
- `tasks`（id, title, workflow_id, stage, column, owner_agent, progress, created_by, created_at）
- `task_events`（id, task_id, type, payload, created_at）— 活动日志 + 群聊通知来源
- `deliverables`（id, task_id, stage, kind[copy|image], content, status[approved|rejected|pending], version）
- `messages`（id, chat_kind[group|private], from, to, body, created_at）
- `workflows`（id, name, stages_json）— 工作流图定义（节点/边/分支/并行分组），工作流卡片数据源，v1 预置「电商新品上架」图
- `agent_executions`（id, agent_id, task_id, stage, model, status[success|failed], input_summary, output_summary, error, duration_ms, created_at）— 执行日志（可观测性数据源，与 task_events 业务事件解耦）

### D6. UI 结构（低保真线框已定稿；开发阶段按 Quiet Signal 设计语言）

- 布局：CSS Grid 三栏（left / main / right），左右可折叠（折叠态宽度 0 + 悬浮展开钮）
- 页面视图：`board`（任务看板）⇄ `task-status`（任务状态栏，含 任务详情/内容交付 标签页）
- 内容交付页：**左右等宽并排两栏**（左 文案成品｜右 图片成品），板块按交付状态驱动显示（尚未产出/生成中 → 占位；待拍板 → 内容 + 采纳/打回；已确认 → 状态标、无按钮）
- 低保真线框阶段（当前）：灰白线框风，只表达结构与交互（文件：`低保真线框-可交互版-多Agent电商工作台.html`）
- 开发阶段视觉：按 quiet-signal-design 的 SPEC.md 落地——canvas #FAFAFA / surface #FFFFFF / ink #0A0A0A·#52525B / line #ECECEE / signal #7C3AED（稀疏、语义化使用）；Display 衬线（Noto Serif SC）+ Body 无衬线（Noto Sans SC）+ 元数据等宽（JetBrains Mono）；大结构直角、小控件 4px、无阴影默认；状态色可保留语义绿（成功/归档）但不得依赖颜色单独传义。组件库以浅封装自建为主，避免引入重型 UI 框架（v1 轻量）

### D6.1 UI 增强策略（用户已确认 2026-09-08）

- **基调不动摇**：Quiet Signal 为主——近白画布、黑色信息层级、衬线 Display 标题、有限紫色信号色、无阴影；低保真线框的三栏结构与各页面元素保持一一对应。
- **gpt-taste 品味注入**：宽容器大标题（H1 不超过 3 行）、章节级大间距（区块如电影章节般呼吸）、克制的滚动/悬停动效（轻量 CSS 或 GSAP 精选一两个场景，如滚动淡入、卡片悬停微缩放）；禁止廉价 meta 标签（如「SECTION 01」）与 emoji 装饰堆砌。
- **Aceternity UI 适度借鉴**：选择性采纳其微交互与组件形态（卡片 hover、焦点光晕、分割线装饰等），**不做**玻璃拟态/强渐变/粒子堆砌；不引入重型组件库依赖，保证页面正常加载与性能。
- **Context7 用法核查**：实现阶段通过 Context7 MCP 获取 React / Vite / Tailwind 的最新 API 用法，避免用过时写法；核心组件实现后对照最新文档复核。
- **生图增强页面**：用 dsh-imagegen（当前渠道 gpt-image-2）生成工位头像、空状态插画、示例场景图等，提升页面丰富性；仅在必要处使用以控制 API 额度。

### D7. 阶段内并行执行：按渠道分组、组间并行、组内串行

- 主图设计/详情图设计阶段可声明并行子任务（多张图）。执行引擎按图片渠道（如不同生图 API/图库）分组：**组间并发、组内串行**，避免同一渠道被限流；每张图完成立即上报 `SUB_TASK_COMPLETE` 事件（WS 推送，前端画廊逐张填充）。
- 并发上限可配置（渠道级），失败子任务不阻塞其余子任务，最终汇总失败清单供拍板参考。
- **理由**：图片生成是耗时大头，多图串行拖慢整条链路；分组并行在参考教程的配图阶段实践中验证有效（并行配图性能优化核心）。
- **备选**：全量串行（简单但慢）；无限制全并行（同渠道易触发限流）。

### D8. Agent 可观测性：执行日志 + 统计（AOP 思路）

- 用统一包装器/装饰器（如 `@withAgentExecution` 装饰 Agent 执行入口，对应参考教程的 AOP `@AgentExecution` 注解思路）自动记录每次执行的 agent/task/stage/model、入参摘要、出参摘要、耗时与结果（success/failed + error），写入 `agent_executions`。
- 执行日志与业务事件（task_events）解耦：执行细节只进 `agent_executions`，业务事件（阶段完成等）仍走状态机事件，避免活动日志被操作噪音淹没。
- 统计接口：按 Agent / 按阶段聚合——执行次数、成功率、平均耗时、耗时分布；工位卡片展示摘要，统计视图展示明细。
- **理由**：多 Agent 各配模型，谁慢谁失败、模型质量如何需要数据说话；实现成本低（单点包装）、对前端零侵入。
- **备选**：不做（无数据支撑 Agent 配置调优与问题排查）；仅手动打日志（无统计、难排查）。

### D9. 真实 LLM 与生图接入（用户已确认 2026-09-08）

- 文案/主管等文本 Agent 调用**真实 LLM API**：不同 Agent 独立配置模型（延续 D3 Worker 注入），渠道与密钥由用户在实现期提供并存入本机配置；模型不可用或未配置时降级。
- 设计师 Agent 输出**真实图片**：通过 dsh-imagegen 生图插件（当前渠道可用模型 gpt-image-2）生成主图/详情图；沿用 D7 渠道分组并行策略规避限流，失败子任务不阻塞。
- **mock 降级开关**：LLM/生图渠道不可用或未配置时，工作台自动降级为内置模拟输出（示例文案/占位图），保证流程可端到端演示与验收；开关在设置面板可见。
- **理由**：产出真实内容才有拍板价值；降级开关保证开发演示不受外部渠道抖动影响（对应 Open Questions 收敛项）。

### D10. 并行开发策略（subagent 分工，用户已确认 2026-09-08）

- 按 capability 边界 + 前后端分层拆分为**可独立交付的任务包**，每个任务包由一个 subagent 负责，并自带验证标准（对应 tasks.md 的 ✓ 验证项）。
- **契约先行**：共享类型包（Agent/Task/Event/Deliverable/Message）最先落地并冻结，作为前后端与各任务包的接口契约，避免并行开发相互阻塞与代码冲突。
- **依赖顺序**：类型包与脚手架（组 1）→ 数据层/引擎（组 2）与后端 API/WS/Agent 运行时（组 3/4）→ 前端壳层与功能视图（组 5/6/7/9）；同层任务包并行，跨层按契约衔接。
- **冲突规避**：每个 subagent 仅允许修改自己任务包声明的文件集合；公共文件（类型包、路由注册、样式基座）由主控统一合并；组 10 统一构建 + 冒烟 + 回归验证。

## Risks / Trade-offs

- [Agent 长时间执行期间前端状态一致性] → 所有状态变更走事件总线 + 单写者（后端状态机），前端只渲染，杜绝双写
- [LLM 输出不稳定导致交付物不合格] → 拍板点 + 主管校对双层把关；打回带修改意见形成闭环
- [SQLite 并发写（多 Agent 并行完成任务）] → WAL 模式 + 单进程写队列；v1 规模足够
- [聊天与任务状态双入口审批（群聊/弹窗/状态栏）可能不同步] → 审批动作统一收敛到后端状态机接口，三处 UI 都是同一 API 的视图
- [Quiet Signal 的克制风格对长文本（文案包）的可读性] → 文案卡片采用层级排版（标题/卖点/大纲/关键词分区），避免整段堆叠；文字层级（Display 标题 + body 正文 + mono 元数据）本身就承担信息结构
- [并行生图触发渠道限流/超时] → 按渠道分组、组内串行、可配置并发上限；失败子任务单独上报不阻塞整阶段
- [图定义引擎实现风险（分支/回退复杂度）] → 图定义与执行引擎分离，支持配置开关降级为线性顺序执行，保底可回退
- [执行日志表持续增长] → 只存摘要级数据 + 定期清理（如保留 30 天或按条数上限）

## Migration Plan

- 全新项目，无既有数据迁移。首版即按上述数据模型建库；`workflows` 表预置「电商新品上架」工作流图定义（6 阶段节点 + 2 拍板点分支 + 校对回退分支 + 并行子任务分组）。
