## Why

挂载是**按定位符引用**的：技能 id = 文件名，文件 id = Vault 相对路径。因此「改文件内容」「新增文件」都不会影响挂载，**只有改名或移动位置会让挂载指向落空**。用户实测提出（2026-09-16）：「技能/文件改名或移动位置就挂载失效，这个有什么办法解决吗」。这是引用型系统的通病（Obsidian 双链、书签、快捷方式同理），但本项目已具备低成本根治的条件：

- 知识库索引（`backend/src/knowledge/indexer.ts`）**已经在为每个 Vault 文件计算 sha1 内容指纹**并落库（`knowledge_docs.hash`，见 `sha1(read.content)`）；
- 症结只在于 `writeIndex()` 是**全量重建**（先 `DELETE FROM docs/links/fts` 再重插），**不留历史**——改名后旧路径直接消失，无从比对。

另有一条佐证说明硬编码不可持续：同类问题此前已用写死的映射表临时修过一次（`backend/src/db/ensure.ts` 的 `FILE_MOUNT_RENAMES`，修 `品牌手册.pdf → 品牌手册.md`，随「挂载有效性可见」需求归档）。

本变更把「改名/移动」从**不可识别**变为**可自动跟随**：靠内容指纹认人，而不是靠名字。

## What Changes

**① 目录快照：留住「上一次的目录」**

- 新增持久化的**目录快照**（条目引用 → 内容指纹），与「当前索引」分离保存；每次索引成功构建后覆盖式更新。
- 快照 SHALL 覆盖两类条目：Vault 文档（复用索引已算的指纹）与技能目录（技能不在 Vault 索引范围内，扫描时现算指纹）。
- 重建索引时以**重建前的快照**为基线比对新目录。

**② 改名/移动识别 + 静默跟随**

- 判定规则（保守）：某挂载引用的目标消失，且当前目录中**恰好一个**条目与其旧指纹相同 ⇒ 认定为改名/移动。
  - 多个候选（内容相同的两份文件）⇒ **不认定**（歧义）；
  - 无候选 ⇒ **不认定**（视为删除，或已同时改过内容）。
- 命中 ⇒ **静默把挂载改写为新引用**，并写后端日志便于排查；用户无感。
- 覆盖范围：`agents.workflow_skills` / `agents.workflow_files` 两个分份列，以及 `agents.skills` / `agents.files` 两个派生并集列同步重算（两者必须一起改，否则分份与并集视图会不一致）。
- 不命中 ⇒ 该挂载照旧不生效，保持既有「失效标红」表现（不改动该行为）。

**非目标**（用户口径 2026-09-16）：

- **不新增任何用户面控件**：不加「一键重新指向」按钮、不加开关、不加提示/通知——「无需用户感知」。
- **不引入稳定 ID**：不给技能文件头加 `id:`、不要求用户在 Vault 笔记里写字段。
- **不做模糊匹配**（名字相似度、mtime、目录邻近）：只认内容指纹，宁可漏也不误指。
- 不改技能目录结构与分类规则；不改挂载分份模型（`workflow_skills` / `workflow_files` 形态不变）。

## Capabilities

### Modified Capabilities

- `workstation`: 「挂载有效性可见」语义扩展——系统在标记失效**之前**先尝试按内容指纹跟随改名/移动；命中即静默改写挂载。原「失效标红 + 可移除」作为兜底完整保留。
- `knowledge-base`: 「文档索引」扩展——持久化目录快照，并在重新索引时识别改名/移动。

### New Capabilities

无。

## Impact

| 文件 | 改动 |
| --- | --- |
| `backend/src/db/schema.ts` · `ensure.ts` | 新增 `catalog_snapshot` 表（幂等建表；`kind/ref/hash`，覆盖式更新） |
| 新增 `backend/src/agents/mount-repoint.ts` | 快照读写 + `diffCatalog()` 识别改名 + `repointMounts()` 改写挂载（含分份与并集）+ 日志 |
| `backend/src/knowledge/indexer.ts` | `writeIndex()` 前后取/落快照并触发比对 |
| `backend/src/agents/skills.ts` | 技能扫描时计算内容指纹；技能索引重建时接入同一套比对 |
| 测试（`backend/src/agents/__tests__/` 或 `knowledge/__tests__/`） | 改名/歧义/删除/无快照/幂等/双列一致 等用例 |
| `docs/开发文档/开发注意事项.md` | 18.x 补「改名跟随」与「快照基线」说明 |

**不受影响**：工作流状态机、任务派发、挂载分份数据模型、注入通道（`buildSystemPrompt` / `buildKnowledgeContext` / `buildHotContext`）、技能库目录结构、Vault 只读承诺（快照与挂载改写都只写自有数据库，不写用户文件）。

**边界（与在建变更的关系）**：`skill-workflow-isolation` 也在动挂载列（分份 + 语义），本变更只增加「引用的重新指向」，不改分份形态；两者合并时的冲突点集中在 `ensure.ts` 与 `skills.ts`，实施时以先合入者为准追加。

**风险**：

- **升级首轮可能漏跟随**：快照尚未建立的第一次索引没有基线可比，此轮不跟随；快照就位后自愈。
- **改名同时改了内容** ⇒ 跟随不到，保持失效（用户口径接受，属预期取舍）。
- **自动改写用户配置**：仅在「唯一指纹匹配」时发生，且改的是「同一份内容的引用」，不改变用户挂载意图；改写动作写日志可回溯。
