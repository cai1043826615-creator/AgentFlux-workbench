## Context

挂载引用现状（经源码核实）：

- 技能 id = **文件名**（`skills.ts` 的 `scanIndex()`：`entry.slice(0, -'.md'.length)`），索引是进程内 `Map<id, path>`；
- 文件 id = **Vault 相对路径**（`skills.ts` 的 `listFiles()`），解析走 `readFileContent(fileRef)` → `vaultAbsPath(root, fileRef)`；
- 存量挂载在 `agents.workflow_skills` / `agents.workflow_files`（分份）与 `agents.skills` / `agents.files`（派生并集）；
- 读路径 `readSkillContent()` / `readFileContent()` 都**每次读盘**，所以「改内容」即时生效；**只有引用本身（名字/路径）变了才会断**。

已有的可复用资产：

- `knowledge/indexer.ts` 的 `sha1(read.content)` **已为每个 Vault 文件算好内容指纹**并存入 `knowledge_docs.hash`；
- `knowledge_docs` 另有 `mtime` / `size`；
- `ensure.ts` 已有 `overlayParts()` / `unionOfParts()` 等分份与并集处理工具（本次可提取复用）。

缺的是什么：`writeIndex()` 全量重建（`DELETE FROM docs/links/fts` → 重插）**不留历史**，所以改名后无从比对。

## Goals / Non-Goals

**Goals:**

- 改名/移动（内容未变）能够被自动识别，并把挂载**静默**改写到新引用
- Vault 文档与技能目录两类条目都覆盖
- 分份列与派生并集列**一起**改写，避免视图不一致
- 判定绝对保守：只在唯一指纹匹配时才动，绝不因歧义或删除而误指
- 全程对用户不可见：不加按钮、不加开关、不加提示

**Non-Goals:**

- 不做稳定 ID（技能文件头 `id:` / Vault frontmatter `id:`）——侵入用户笔记，且复制文件会撞 id
- 不做模糊匹配（名字相似度 / mtime / 目录邻近）——宁可漏，不可误指
- 不做失效项的「一键重新指向」UI（用户明确：无需感知）
- 不改挂载分份模型与技能目录结构
- 不改「失效标红」既有行为

## Decisions

### 1. 引用身份：保持名字/路径为存储键，用「指纹跟随」补齐（不改成稳定 ID）

**替代方案**：给每条内容发稳定标识（技能文件头 `id:`、Vault 文档 frontmatter `id:`），挂载存标识。

**否决理由**：对用户 Vault 笔记侵入性大（要求每条都写字段，且用户可能用别的工具同步）、复制文件会撞 id、还需一次性回填存量（又要引入一次迁移与标记）。而**指纹已经现成**（索引已算），成本低一个量级。代价是「改名+同时改内容」跟不到——但这条用户已接受。

### 2. 快照存哪：新增小表 `catalog_snapshot(kind, ref, hash)`

**替代方案**：塞进 `settings` 表的两个 JSON 键（`catalogSnapshot:docs` / `catalogSnapshot:skills`）。

**取舍**：就数据量而言（当前 11 文档 + 7 技能）两者都够。选**表**的理由是：按 `kind` 天然分区、覆盖式更新可以走 `tx()`（先 DELETE 同 kind 再批量 INSERT）保证原子性、将来若要留 rename 历史或加 `mtime` 只是加列。settings 存大 JSON 不利于后续查询与迁移。

**注意**：快照是**基线**，与「当前索引」是两份数据——基线必须取自**上一次构建的目录状态**，不能被本次构建覆盖后再去比对。

### 3. 判定规则：唯一指纹匹配才跟随

对每个解析失败的挂载引用 `ref`：

1. 查快照中 `ref` 的旧指纹 `h`；**无记录**（首轮升级、快照未建立）⇒ 本轮不跟随，直接结束；
2. 在当前目录里找指纹 == `h` 的条目集合 `C`；
3. `|C| == 1` ⇒ 跟随，把 `ref` 改写为 `C` 中那条的新引用；
4. `|C| > 1` ⇒ **歧义，不跟随**（保持失效）；
5. `|C| == 0` ⇒ **不跟随**（视为删除，或改名同时改了内容）。

**额外防呆**：若目标新引用**已经**被同一处（同一 Agent 同一份）挂载，则只去重、不新增重复条目。

### 4. 触发时机：索引构建成功后统一处理（不在读路径上做）

跟随在「索引成功构建后」一次性处理，覆盖全部挂载：读路径（`readSkillContent` / `readFileContent`）保持纯粹，不做重活。技能侧在技能索引重建时走同一套比对（技能索引是进程内惰性构建，需在构建时落快照）。

**取舍**：意味着「改名后需要等一次索引刷新才被跟随」。这是有意的——跟随本身依赖目录比对，没有刷新就没有新目录可比。技能侧走界面上传会立即失效重建索引，因此立即跟随；手工改文件则需等下一次扫描（重启后端或触发重建）。

### 5. 静默：只写后端日志，不做任何用户面呈现

用户口径（2026-09-16）：「无需做一个按钮什么的给用户用或者感知到」。跟随动作写 `console.warn` 级别的后端日志（旧引用 → 新引用、影响条数），便于排查；**不进任务事件、不弹提示、不加设置开关**。既有「失效标红」保持不变（那是既有行为，不是本次新增的提示）。

### 6. 只认内容指纹，不做模糊匹配

宁可漏（保持失效，用户用既有挂载弹窗手动重挂）也不误指。理由：挂载内容会**真实进入 prompt**，误指的代价是产出错内容（比失效更难发现、更伤），而失效是可见且可修的。

## Risks / Trade-offs

- **升级首轮漏跟随**：快照首次建立前没有基线 ⇒ 当轮不跟随。需在文档中写明；此后自愈（下一次索引起具备能力）。
- **改名 + 同时改内容**：指纹对不上 ⇒ 跟随不到，保持失效。属预期取舍（用户已接受）。
- **内容完全相同的两份文件**（如复制的模板）：歧义 ⇒ 不跟随。安全侧，但用户可能困惑「为什么它不跟」→ 靠日志说明。
- **自动改写用户配置**：仅在唯一指纹匹配时发生，且是「同一份内容的引用改写」，不改变挂载意图；日志可回溯。这是本变更唯一会写用户配置的地方，须与「代码不得持续拥有运行期配置」的既有铁律协调——本变换是**事件驱动的单次改写**，不是每次启动的对账，不违反该铁律。
- **并集列与分份列不同步**：改写须两处一起做，否则 `agents.skills` 会残留旧引用（表现为并集里多一个失效项）。实施时抽同一个函数处理，禁止只改一处。
- **快照与实际索引不一致**（构建中途失败）：快照仅在**构建成功后**落库，失败则不更新，保证基线始终对应一次成功状态。
- **错过的跟随不可追溯（实测确认的固有限制）**：跟随只能从「曾进入过基线」的引用出发。若某挂载在基线建立**之前**就已失效（例如该引用在功能上线前就被改名了），它从未进过任何基线，没有指纹可反查，此后无论再改多少次名都接不回来——与引入本功能之前的行为一致（失效、需手动重挂）。
  这不是缺陷而是「宁漏不误」的必然代价：没有旧内容指纹就无法证明「新文件就是原来那个」。已在 `mount-rename-follow.test.ts` 中用断言固化该行为，避免被误当成 bug 反复排查。
